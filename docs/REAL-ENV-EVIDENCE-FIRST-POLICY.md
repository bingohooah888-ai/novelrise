# NOVELIGHT — 実環境証拠優先・再試験抑制ポリシー

Version: 1.0 / 2026-10-29

この文書は、NOVELIGHTの開発・監査・デプロイ・Staging/Preview実証・外部API連携で、**単体テストが通っただけで「完成」と宣言し、実環境の失敗が出るたびに小修正と承認を反復する事故**を防ぐための永続ポリシーである。正式なMASTERと `AGENTS.md` を上位基準とし、既存の安全・承認ゲートを緩和しない。特にAuth、RLS、Stripe、Secret、Staging/Productionで適用する。一般の低リスクFAST PATCHに一律の実環境E2Eを課さない。

## 1. 新チャット／別エージェントの開始契約

- チャットの記憶に頼らず、**最新mainの `AGENTS.md` → 本ポリシー → 該当MASTER節 → 現行branch/PR** を参照する。古いチャットは現在状態の根拠にしない。
- NLOとRemote Desktop Commanderを混同しない。Source of Truthと実行手段の既存優先順位を維持する。
- 最新の「何が実証済みで何が未実証か」を、PR/Issueの**短い証拠台帳**から再構築する。次チャットで完了済みの検証や使用済み承認を再実行しない。

## 2. 完了の4区分（必須）

開発や修正の報告では、最低限次を区別する。

1. **実装済み**：コード・文書・テストを書いた。動作保証ではない。
2. **ローカル／CI確認済み**：実際に実行されたテスト名と結果を証拠付きで示す。モック・静的検証はここまで。
3. **実環境検証済み**：指定したVercel Preview/Production、Supabase Staging/Production、外部APIなどで実際に確認できた範囲・日時・deployment/SHA・HTTP/DB結果を示す。
4. **公開・運用確認済み**：必要な承認後に反映された本番対象で、ユーザー影響・正常応答・復旧可能性を確認した。

**本当に終わっていない実環境試験を「すべて完了」「動作確認済み」「次はほぼ通る」と表現しない。** テスト合格だけでは実環境の成功を保証しない。予測は未検証要因を明示し、根拠のない成功確率を提示しない。

## 3. 高リスク実証の前提表（最初に作る）

Auth、JWT、Vercel認証保護、RLS、決済、migration、外部API等のFULL PREFLIGHT作業では、実行前に次の依存経路を列挙する。

- **契約**：GitHub SHA/branch、Vercel deployment/project、APIのレスポンス**生の形**（connectorが正規化した表示との違いも確認）、headers・認証方法、Supabase project/role、DB schema、timeouts。
- **段階**：単体静的 → 実API read-only → Preview read-only → 必要な承認済み最小write/probe → cleanup → 独立残留監査。
- **各段階の合格証拠**：対象、実行方法、予想結果、実結果、未確認事項、次段階へ進む条件。
- **失敗と費用**：破壊的処理・課金・Staging/Previewの承認が要る境界、rollback/cleanup、再試行の制約。

本来read-onlyで独立検証できるAPIの形・権限・保護設定・Preview疎通は、**一回限りの実JWT/write承認を消費する前に**可能な範囲で確かめる。読み取りでも既存ポリシー上のStaging承認が必要な操作は、事前にその範囲の明示承認を取得する。ツールや権限が不足する場合は「未検証」として理由を残し、安全ゲートを迂回しない。

## 4. 試験失敗時の停止・切り分け規則

1. **失敗を検知したら同じ承認・同じ試験を自動再実行しない。** 一回限りの承認は成功でも失敗でも消費扱いとし、GitHub承認台帳の状態を再確認する。
2. 失敗箇所をステップ／API単位で特定する。必要な診断は**固定された段階名と範囲を限定した結果区分**のみとし、Secret、Auth token、cookie、パスワード、個人データ、HTTP本文、未加工エラー、接続文字列をログに出さない。
3. **最小の失敗工程を先に独立再現・read-onlyで検証**し、API公式仕様・生レスポンス形・認証範囲・本番との差異を照合する。曖昧な推測でコード修正を連発しない。
4. 修正には、根拠・変更差分・反例テスト（誤った応答や保護無効を拒否するもの）を付ける。安全な認可、保護、権限、cleanupの条件を「PASSにするため」緩めない。
5. **同種失敗が2回続いたら同じ手順での承認消費を停止**し、原因分類と実行経路を見直す。修正なしの再試験は原則禁止。繰り返し同じ外部API境界で失敗する場合は、実JWT全体ではなく独立した最小read-only診断経路へ切り替える。
6. 外部事情でread-only検証不能なら、残りのリスクを正直に示し、**新しい承認**を得るまで書き込み・本番変更・実JWT試験を止める。

## 5. 1つの問題に対する修正単位と費用

- 同じ根因に属する互換性・レスポンス形・疎通・認証方式は**可能な限り同じDraft PRでまとめて診断し、focused testと必要なCIを通してから**承認を求める。関係のない機能や別の承認境界を巻き込まない。
- 機械的なlint/Prettier等は `docs/MECHANICAL-CORRECTION-POLICY.md` に従い、推測修正を繰り返さない。
- 一時診断の継続利用価値を評価し、必要なら共通機構化し、不要なら撤去する。
- **「本番承認」は高リスクmain/Production反映に限る。** 「ステージング承認」と相互代用しない。後者はexact main SHA、候補、scope、**1回**に結び付け、失敗時も消費する。承認済みの範囲を広げない。

## 6. 実行証拠台帳と次チャット引継ぎ（必須）

高リスクworkstreamのPR/Issueに、次を短く残す。

- 現在の `main` SHA、branch/PR、Preview deployment ID・Staging project ref（必要時）
- 各ステップの **PASS / FAIL / NOT RUN / BLOCKED** と、ログ・CI・API・SQL等の根拠
- 実環境で**未検証**の工程と、次の最小確認・失敗原因
- 認証/個人データ/DBの残留件数、cleanup/rollback、Production影響
- 各承認の **未取得 / 承認済み / 使用済み**、次に必要な承認
- 新チャット開始時の「済んだこと／次にすること」を事実で区分し、すでに成功済みの工程を繰り返さない。

## 7. 最終ゲート

- 安全ゲートは保持する。**静的テスト成功だけで実環境成功と宣言しない。**
- 実環境の未検証工程がある場合は「部分完了／実環境未検証」と明記する。
- Production反映・Staging試験・課金・高リスク操作に必要な既存の明示承認を省略しない。
- 本ポリシーの運用変更は `AGENTS.md`、MASTER、必要なテストを同じPRで更新し、差分・CIを確認してから正式反映する。
