# NOVELIGHT WORK EXECUTION PREFLIGHT

**NOVELIGHT 実作業・自動化優先・手動操作最小化チェック**

本書は `docs/NOVELIGHT-MASTER.md` の作業時間可視化、工程切替・再見積もり、効率化、作業開始ゲート、作業完了ゲートを実行時に落とさないための補助Preflightである。

MASTERが常に上位基準であり、本書はMASTERを置き換えない。

## 1. 発火条件

次のいずれかを行う前に、このPreflightを通す。

- コード変更、GitHub操作、CI/E2E、デプロイ、Vercel、Supabase、Stripe等の開発・外部サービス操作
- デザイン、画像、X、マーケティング、広告、分析、資料更新等でツール実行・生成・編集・更新を伴う作業
- 前日の続き、既存PR・既存ブランチ・既存Workflow・デプロイ作業の続行
- 主要工程から別の主要工程へ切り替える作業

相談・質問・評価のみでツール実行を伴わない場合は対象外とする。

## 2. 作業開始ゲート

### 2.0 実行ターン・ハードリセットゲート

**実行ターン**とは、ユーザーから1通の新しいメッセージを受け、その応答内でNOVELIGHTに関するツール呼び出し・外部操作・ファイル変更を行う1回のアシスタントターンを指す。

NOVELIGHTでツールを1回でも使う実行ターンでは、**そのターンの最初のユーザー可視メッセージを可視実行カードにする。カード送信前のツール呼び出しは禁止する。** 読み取り専用のGitHub確認、Connector discovery、最新main取得、状態確認も例外にしない。

可視実行カードは、その実行ターンだけで有効とし、**次のユーザーメッセージを受けた時点で必ず失効する。前ターンのカードを再利用してはならない。** 次のような入力もすべて新しい実行ターンとしてカードを再発火する。

- 「はい」「続けて」「次へ」等の継続指示
- スクリーンショット、画面状態、ログ、エラー結果の共有
- ユーザー本人の手動操作が完了したという報告
- 途中で必要だった認証・設定・保存・再デプロイ等の完了報告
- 前ターンで停止していた外部処理の続行依頼

同じ目的の続き、同じチャット、数分前の報告、作業が短いことはカード再発火を省略する理由にしない。

カード送信後、最初のツール群は正式基準を取得するための読み取り専用Bootstrapとして扱う。そこで最新main、main上のMASTER / Preflight、禁止・安全境界を確認するまでは、変更・更新・デプロイ・外部state mutation等の実作業へ進まない。

この順序を固定する。

1. **可視実行カードを送信**する
2. 読み取り専用Bootstrapで最新main、MASTER、Preflightを確認する
3. 禁止・ロック・Environment / Branch / Production / Secret境界を確認する
4. 自動化経路を選ぶ
5. 変更を伴う実作業を開始する

最初のツール操作より前に、以下を満たす。

- [ ] 今回の最終ゴールを一文で定義した
- [ ] 実行環境が時間見積もりを許可する場合、**トータル予想時間**をユーザーへ提示した
- [ ] 実行環境が時間見積もりを許可する場合、主要工程ごとの予想所要時間をユーザーへ提示した
- [ ] 外部待ち時間、待機要否、次工程が完了待ちかを提示した
- [ ] ユーザーに必要となる手動操作の種類と概算回数を提示した
- [ ] このカードは前ターンからの流用ではなく、現在の実行ターンで送信した

変更を伴う最初の実作業より前に、以下を満たす。

- [ ] 最新mainを再取得した
- [ ] main上の `docs/NOVELIGHT-MASTER.md` を正式基準として再読込した
- [ ] main上の `docs/WORK-EXECUTION-PREFLIGHT.md` を再読込した
- [ ] 禁止・安全境界を確認した

最新main、正式MASTER、禁止・安全境界の確認が欠けている場合は実作業を開始しない。時間見積もりだけが実行環境の上位制約によって禁止・非対応の場合は、後述のDegraded-Continueを適用する。

### 2.1 可視時間報告 Fail-Closed ゲート

時間見積もりを提示できる実行環境では、内部で考えただけでは未実施とする。**ユーザーが読めるメッセージとして現在の実行ターンで送信済みであること**を開始条件とする。

実作業開始前の可視実行カードは、原則として次を含める。

- `トータル予想時間`: 実行環境が許可する場合、作業全体の現実的な幅
- `主要工程`: 工程の内容。実行環境が許可する場合は工程ごとの予想時間も含める
- `手動操作`: ユーザー本人に必要な操作の有無と概算回数
- `待機要否`: 外部待ちがある場合、ユーザーが待つ必要があるか

#### Hard Fail-Closed

次の不足は安全性・正式基準に直接関係するため、**変更を伴うツール実行禁止**とする。

- 最新mainまたはmain上のMASTER / Preflightを確認できない
- 禁止・ロック、Production境界、Secret境界が不明
- 実行対象のEnvironment、Branch、Deployment等を安全に確定できない
- Production、高影響変更、課金、Secret、破壊的操作等で必要な承認がない

また、時間見積もりを提示できる環境で現在の実行ターンの可視実行カードを送信していない場合は、**読み取り専用Bootstrapを含めツール呼び出し禁止**とする。

#### Degraded-Continue

実行環境の上位制約によって時間見積もり等の一部表示が禁止・非対応である場合、**時間報告不能だけを理由に安全・可逆・既承認スコープ内の作業を停止しない。**

この場合は、可能な情報で可視実行カードを作る。

- 今回の目的
- 主要工程
- 手動操作の有無
- 待機要否
- 時間見積もりを省略する実行環境上の理由

Degraded-Continueでもカード自体は現在の実行ターンで送信し、前ターンのカードを再利用しない。

Degraded-ContinueはProduction、Secret、課金、破壊的操作、安全境界不明等のHard Fail-Closedを回避するためには使用できない。

「前のターンで似た説明をした」「短い作業だから」「継続作業だから」は、正式基準・禁止確認・可視実行カードそのものを省略する理由にはしない。

主要工程が完了して次の主要工程へ移る場合も、残り工程を再評価する。時間見積もりが許可されており、当初見積もりから5分以上または概ね25%以上ずれる見込みが判明した場合は、次の実操作より前に更新見積もりをユーザーへ報告する。

### 2.2 時間報告の固定フォーマット

時間見積もりを提示できる環境では、必要以上に長い説明を避けるため、通常は以下の短い形式を使う。

`トータル予想時間：○〜○分。内訳：①○○ ○〜○分、②○○ ○〜○分、③○○ ○〜○分。手動操作：0回（または約○回）。待機：不要（または外部処理中は待機不要）。`

文言は状況に応じて自然に変更してよいが、時間見積もりを提示する場合は**トータル時間を落とさない**。工程別だけを伝えてトータルを省略しない。

実行環境の上位制約で時間見積もりを提示できない場合は、次の形式へ切り替える。

`目的：○○。主要工程：①○○、②○○、③○○。手動操作：0回（または約○回）。待機：不要（または外部処理中は待機不要）。時間見積もり：実行環境の上位制約により省略。`

### 2.3 実行可能 Runtime Gate

リポジトリを操作できる実装エージェントでは、文書を読んだつもりで終わらせず、主要工程の入口でRuntime Gateを実行する。Runtime Gateは、**現在の実行ターンで可視実行カードを送信したという明示的な証跡がない場合にFAILする。**

通常の時間見積もりカードでは、例えば次のように実行する。

```text
npm run runtime:gate -- --phase=<phase> --card-visible --card-total=<total> --card-steps=<steps> --card-manual=<manual> --card-wait=<wait>
```

実行環境の上位制約により時間見積もりを出せないDegraded-Continueでは、`--card-mode=degraded` と `--card-reason=<reason>` を追加し、`--card-total` を省略できる。

同じ情報は `NOVELIGHT_EXECUTION_CARD_VISIBLE`、`NOVELIGHT_EXECUTION_CARD_MODE`、`NOVELIGHT_EXECUTION_CARD_TOTAL`、`NOVELIGHT_EXECUTION_CARD_STEPS`、`NOVELIGHT_EXECUTION_CARD_MANUAL`、`NOVELIGHT_EXECUTION_CARD_WAIT`、`NOVELIGHT_EXECUTION_CARD_REASON` の環境変数でも渡せる。

`phase` は `start`、`implementation`、`github`、`ci`、`deploy`、`vercel`、`supabase`、`stripe`、`files` のいずれかとする。

このコマンドはカード証跡を確認した後、`origin/main` を再取得し、最新mainの `docs/NOVELIGHT-MASTER.md` と `docs/WORK-EXECUTION-PREFLIGHT.md` を直接取得可能であることを確認する。通過状態は `.git/novelight-runtime-gate.json` に記録する。最新版取得に失敗した場合はFail-Closedする。

実装前に使用する `npm run preflight:agent` は、このRuntime Gateを先頭で実行するため、実行カード証跡を環境変数または引数相当で与えていない場合は開始させない。

Connectorやクラウド実行環境でローカルnpmコマンドを実行できない場合は、**現在のアシスタントターンで可視実行カードを先に送信していることを同等のFail-Closed条件**とし、その後にConnector/APIで最新mainのSHA、MASTER、Preflightを直接再取得する。コマンドを使えないこと自体を、カード送信や正式基準の確認省略理由にはしない。

## 2.5 禁止・ロック・ツール選定ゲート

ツールを呼び出す前に、今回の作業に適用される明示的な禁止事項・ロック・実行環境の制約を先に抽出し、**禁止リストとして固定してから**ツール候補を選ぶ。

禁止事項は、ユーザーの現在の明示指示、当該作業の引き継ぎ条件、MASTER、正式な補助文書の順に確認する。局所的な利便性やツールの自動選択を理由に、明示的な禁止を上書きしない。

### Fail-Closed原則

- 禁止対象に該当するツール・操作は、候補段階で除外する
- 禁止に該当するか不明な場合は実行せず、安全な代替手段を選ぶ
- 「確認のため」「スクリーンショットを見たため」「自動ルーティングされたため」等を禁止解除の理由にしない
- ユーザーが明示的に解除するまでロックは継続する
- 禁止事項と作業効率が衝突する場合は、効率より禁止事項を優先する

### ツール呼び出し直前チェック

各ツール呼び出しの直前に、少なくとも以下を満たす。

- [ ] このツールは現在の禁止リストに抵触していない
- [ ] このツールは今回の目的達成に本当に必要である
- [ ] より安全・自動・少ない手動操作の代替がないか確認した
- [ ] ユーザーが指定した実行環境・担当境界を越えていない
- [ ] 判断に不確実性がある場合は実行を止めた

1項目でも満たせない、または不明な場合は、そのツールを呼び出さない。

### ノクター画像作業の現行ロック

ユーザーが明示的に解除するまで、NOVELIGHT公式マスコット「ノクター」の画像生成・画像編集については以下を固定する。

- ChatGPT側の画像生成・画像編集ツールは使用禁止
- ノクターの画像生成・画像編集の実行環境はComfyUIのみ
- ChatGPTはComfyUIワークフロー設計、JSON作成・修正、設定値設計、操作案内、画像の閲覧・分析のみ担当する
- ComfyUIのスクリーンショット確認、画像内容確認、操作案内を理由にChatGPT側の画像生成・編集ツールを呼び出してはならない

### ツール・ホワイトリスト方式

禁止リストだけに依存せず、**作業種別ごとに使用可能ツールを先に固定するホワイトリスト方式**を併用する。

ツール実行前に、内部的に少なくとも次の4項目を確定する。

- `task_type`: 今回の作業種別
- `allowed_tools`: 今回使用してよいツール・実行環境
- `denied_tools`: 今回使用してはならないツール・実行環境
- `unlock_condition`: ロック解除に必要なユーザーの明示指示

**`allowed_tools` に入っていないツールは、便利そう・自動選択された・画像が表示された等の理由で追加してはならない。**

作業種別を一意に分類できない場合は、新しいツールを呼び出す前に分類を確定する。分類不能なまま実行することを禁止する。

#### ノクター / ComfyUI 作業の固定ホワイトリスト

| 作業種別 | 使用可 | 使用不可 |
| --- | --- | --- |
| ComfyUIワークフローJSONの作成・修正 | JSON/ファイル操作、Python等のテキスト・構造編集、GitHub等の必要なファイル管理 | ChatGPT側の画像生成・画像編集 |
| ComfyUIスクリーンショット確認 | 画像の閲覧・分析、テキストによる操作案内 | ChatGPT側の画像生成・画像編集 |
| ComfyUI生成結果の評価 | 既存画像の閲覧・分析、設定値・プロンプト・ワークフロー改善案 | ChatGPT側の画像生成・画像編集 |
| ノクター画像の実生成・実編集 | **ComfyUIのみ** | ChatGPT側の画像生成・画像編集 |

ノクター作業では、ChatGPT側の画像生成・画像編集ツールを「禁止されている候補」として残すのではなく、**原則として最初からツール候補集合へ入れない**。

#### ロック解除条件

次のような一般的な継続指示は、画像生成ロックの解除とは解釈しない。

- 「はい」
- 「続けて」
- 「作って」
- 「改善して」
- 「次へ」

ChatGPT側の画像生成・画像編集を再び使用可能にするには、ユーザーが **ChatGPT側の画像生成ロックを解除する意思を明示的かつ直接的に示すこと** を必要条件とする。

解除指示が曖昧な場合はロックを維持する。

### ツール選択の決定順序

ツールを選ぶときは、次の順序を固定する。

1. 作業種別 `task_type` を確定する
2. 適用中の禁止・ロックを抽出する
3. `allowed_tools` / `denied_tools` を固定する
4. `allowed_tools` の中だけで、自動化・安全性・手動操作最小化を比較する
5. 実行直前に許可表と再照合する
6. 不一致・不明点があれば実行せず停止する

「最適なツールを自由に選び、その後で禁止事項を確認する」順序にはしない。

## 3. 自動化優先ゲート

人間が画面を何度もクリック・コピー・貼り付けする経路を既定にしない。作業開始時と主要工程切替時に、次の順で最短かつ安全な経路を検討する。

1. 既に接続済みの専用ツール・Connector・API
2. 公式CLI
3. 既存スクリプト・既存Workflow
4. 安全な一括コマンドまたは小さな補助スクリプト
5. UI手動操作

UIが最初に見えているという理由だけでUI経路を継続しない。

### 手動操作3回ゲート

同一工程でユーザーの手動操作が **3回を超える見込み**になった場合、そのまま案内を続けず、次を再評価する。

- CLI/API/Connectorへ切り替えられないか
- 複数操作を安全な一括コマンドへまとめられないか
- 一度だけの補助スクリプトで再利用可能にできないか
- 既に取得済みの情報を再入力させていないか
- こちら側で確認できる内容をユーザーに確認させていないか

安全な代替がある場合はそちらへ切り替える。代替がない場合だけ、手動継続の理由を短く説明する。

## 4. 「1操作ずつ」の解釈

ユーザーが「1操作ずつ」と指定した場合も、クリック1回・キー入力1回ごとに機械的に停止する意味にはしない。

**1操作 = 失敗時の影響範囲が明確で、途中で安全に止められる1つの論理操作** とする。

例:

- 良い: 「この確認コマンドを1回実行する」
- 良い: 「この環境変数6件を安全なスクリプトで一括設定する」
- 悪い: `n` を押す → Enter → ブラウザへ戻る → Copy → VS Codeへ戻る、を毎回別ターンに分解する

ただし、2FA、OAuth承認、秘密値の取得・入力、本番変更の最終承認、破壊的操作等、ユーザー本人の判断や資格情報が必要な場面は1操作ずつ停止してよい。

## 5. ユーザー操作の分類

作業開始時と工程切替時に、操作を次の3種に分類する。

### A. ChatGPT/ツール側で処理する

原則としてユーザーへ渡さない。

- GitHub状態確認
- 差分確認
- CI/Workflow状態確認
- コマンド組み立て
- 非機密設定の一括処理
- 読み取り専用検証
- ログ・エラー解析

### B. ユーザー本人だけが行う

必要な場面だけ案内する。

- 2FA
- OAuth/アカウント承認
- SecretやAPI keyの取得
- Secretのローカル入力
- 決済・本番変更等の明示的承認

### C. 安全確認として残す

自動化で削らない。

- 本番対象の再確認
- production/staging分離確認
- rollback/backup確認
- 破壊的変更直前の確認

## 6. 秘密値・認証ゲート

- Secret、API key、2FAコード、Recovery code等をチャットへ貼らせない
- 秘密値はユーザー端末または外部サービス画面内だけで扱う
- 非機密値と秘密値を区別し、秘密でない値まで不要にSensitive扱いしない
- Production値とStaging/Test値を混在させない
- 本番値の流用が疑われる場合はfail closedする

## 7. 工程切替・再見積もりゲート

次のような主要工程の切替では、そのまま次のツール操作へ進まない。

- UI → CLI
- CLI → GitHub
- GitHub → CI/E2E
- 設定 → Redeploy
- Redeploy → Smoke test
- 実装 → PR
- PR/CI完了 → 次機能

切替時に以下を再確認する。

- [ ] 次工程の規模とリスクを再評価した
- [ ] ユーザー手動操作は何回必要か
- [ ] 新たに自動化できる箇所はないか
- [ ] 外部待ち時間はあるか
- [ ] 次工程が前工程の完了待ちか
- [ ] リポジトリ操作可能なエージェントでは対応する `runtime:gate` phaseを通したか

同じアシスタントターン内の工程切替では、当初見積もりから5分以上または概ね25%以上ずれる見込みが判明した場合に更新カードを送る。**ユーザーへ一度ターンを返した場合は、ずれの大小に関係なく次の実行ターンでカードを新規送信する。**

時間見積もりを提示できる実行環境では、10分超に変わった場合はツール操作前に新しい時間見積もりを報告する。実行環境の上位制約で時間見積もりを提示できない場合は、工程規模・手動操作・待機要否の更新だけを可視化し、安全な作業は継続する。

### 7.1 短時間外部待機・自動継続ゲート

GitHub Actions、CodeQL、Vercel Deploy、Smoke/E2E等の外部処理が実行中で、**残り待ち時間が概ね10分以内と見込まれ、同一ターン内で状態確認を継続できる場合**は、原則として完了まで追跡する。

次のような「途中状態だけの応答」でユーザーへターンを返し、再度「はい」「続けて」と言わせる運用を既定にしない。

- 「まだ実行中です」
- 「完了待ちです」
- 「次の結果が出たら確認します」

短時間待機では、一定間隔で状態確認し、完了したら**同じターンで結果確認・必要なログ診断・安全に自動実行できる次工程まで続行**する。

途中でユーザーへ返してよいのは、次のいずれかに限る。

- 10分を超える待機へ延びる見込みになった
- ユーザー本人の承認・Secret入力・2FA・画面操作が必要になった
- 失敗原因が複数あり、ユーザー判断なしに安全な分岐を選べない
- ツールまたは接続制約により同一ターンで追跡を継続できない
- 安全性・本番影響等の理由で明示承認が必要

外部処理が失敗した場合も、「失敗しました」で止めず、ログ取得・原因特定・安全な修正が可能ならそのまま次へ進む。

## 8. 反復失敗ストップゲート

同じUI経路、同じクリック、同じ検索、同じコマンドが **2回連続で期待どおり進まない**場合、同じ手順を3回目まで機械的に繰り返さない。

その時点で原因を再分類し、CLI/API/別画面/別検証方法等へ切り替える。

ユーザーが「さっきと同じ」「出ない」「押せない」と指摘した場合は、操作説明を繰り返す前に、現在の仮説が誤っている可能性を優先して再評価する。

## 9. 作業完了ゲート

準備だけで終了しない。今回の最終ゴールに対する実成果まで進む。

- 設定作業なら、設定値を入れただけでなく反映確認まで行う
- デプロイなら、Ready表示だけでなく必要なSmoke/Revision確認まで行う
- CI改善なら、PR作成だけでなく該当CI結果まで確認する
- 文書改善なら、実ファイルへの反映と差分確認まで行う

ただし、ユーザー本人しか行えない認証・Secret入力・本番承認が未完了の場合は、その地点を合理的な停止理由として明示する。

## 10. 送信前セルフチェック

実作業中の応答を送る前に、少なくとも以下を確認する。

- [ ] MASTERより局所的な指示を優先していない
- [ ] 今回の `task_type` を確定した
- [ ] `allowed_tools` / `denied_tools` を固定した
- [ ] 実行しようとしているツールが `allowed_tools` に含まれている
- [ ] 現在の禁止リストに抵触するツール・操作を候補に残していない
- [ ] ユーザー指定の実行環境・担当境界を越えていない
- [ ] ユーザーへ不要な手作業を増やしていない
- [ ] 3操作超ゲートを越えていない
- [ ] 同じ失敗操作を3回目まで繰り返していない
- [ ] 工程切替時の再評価を落としていない
- [ ] ツールを使う現在の実行ターンで、**最初のユーザー可視メッセージとして可視実行カードを送信済みである**
- [ ] 前ターンのカードを流用していない
- [ ] 実行環境が許可する場合は**トータル予想時間をユーザーへ可視化済みである**
- [ ] 時間見積もりを提示できない場合は、目的・主要工程・手動操作・待機要否・制約理由を可視化済みである
- [ ] 10分以内の外部待機を「実行中です」だけで返していない
- [ ] Secret/2FA以外でこちらが処理できる内容をユーザーへ返していない
- [ ] 準備工程を最終成果と誤認していない

このPreflightの目的は、ルールを覚えていることを期待するのではなく、**実行時に必ず確認する構造へ変え、同じ運用ミスを再発しにくくすること**である。
