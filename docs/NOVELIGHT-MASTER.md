# NOVELIGHT MASTER

**プロジェクト基本方針・運営原則・長期ビジョン**

**最終更新：2026年9月26日**

## 1. NOVELIGHTとは

NOVELIGHT（ノベライト）は、作者と読者の双方が長く小説に関わり続けられる環境を作ることを目的とした小説投稿プラットフォーム。

既存の小説投稿サービスでは、作者の知名度や既存ファン数などによって、作品そのものが評価される以前に「そもそも読まれない」という問題が起こり得る。

NOVELIGHTでは、この「評価される前の機会格差」をできる限り小さくする。

作者が課金することで買えるものは「高評価」や「ランキング順位」ではなく、あくまで読者の目に触れる機会である。

その先で作品が評価されるかどうかは、作品そのものと読者に委ねる。

基本思想

「すべての物語に、光を。」

NOVELIGHTの課金は、勝つための課金ではない。

作品が評価の舞台に立つまでの距離を縮めるための課金である。

## 2. 作者に対する基本思想

作者の知名度や実力をNOVELIGHT側が決めつけない。

作者自身が、自分に必要な環境を判断する。

無料プランでも十分読者を獲得できる作者であれば、無理に課金する必要はない。

一方、

「作品には自信があるが、そもそも読んでもらえない」

と感じる作者は、有料プランによって読者の目に触れる機会を増やすことができる。

NOVELIGHTは作者に成功を販売しない。

作品を読者の前へ届ける機会を提供する。

ランキングや作品評価については、最終的に作品の実力と読者の判断によって決まる環境を目指す。

## 3. 読者に対する基本思想

NOVELIGHTでは、読者が同じ人気作品だけを読み続けるのではなく、多くの作品へ触れ、新しい作品を発掘する文化を作る。

その中心となる仕組みが「LIGHT SEED」である。

読者は無名・新規作品を発掘し、その作品が後に評価された場合、自分自身の「SCOUT RECORD（スカウトレコード）」を積み上げることができる。

SCOUT RECORD、Scout Level、Scout Rank、読者称号、Scout Point等によって、

「面白い作品を探すこと自体が楽しい」

という体験を作る。

SCOUT RECORDはβ版から読者向け主要機能として本実装する。目的は実績収集そのものではなく、読者が新しい作品を探し、無名・新規作品を発掘し、評価・反応を返し、その作品の成長を見届ける理由を増やすことである。

SCOUT制度では、成長を表すScout XPと、将来利用できる報酬資源であるScout Pointを分離する。Scout XPは消費せず、Level / Rankの成長へ利用する。Scout Pointはβ版から獲得・残高表示を行うが、β期間中は原則として利用不可とし、正式リリース後のAI利用特典等への交換を予定する。

SCOUT RECORDには、正当なLIGHT SEED履歴、発掘成功、称号その他の生涯実績を残す。Scout Rankや公開称号は他ユーザーから確認できる実績表現として利用できるが、高Rankユーザーの評価・コメントを作品Rankへ強く加算する等、人気SCOUTが作品評価を支配する仕組みにはしない。

β版の具体的なScout XP、Scout Point、読者称号 / 作者称号 / 限定称号、Lv.30上限、公開範囲、不正対策、KPI、UI方向は第38章および第49章を正式基準とする。

毎日の作品発見導線

読者が日常的にNOVELIGHTを開き、新しい作品を探す習慣を作るため、毎日の作品発見導線を導入候補とする。

読者の好み、新作、未発掘度、過去の閲覧傾向等を参考に、その日に読む候補を少数提示する。

Free作品を含む全作品を掲載対象とし、課金額だけによって毎日の作品発見導線を独占できる設計にはしない。

LIGHT SEED、LIGHT CHECK、SCOUT RECORD等へ自然につながる導線とし、「今日もNOVELIGHTで何か発掘したい」という継続利用理由を作る。

提示数、選出方法、推薦比率等はβ版の実データから調整する。

発見スタイル選択

毎日の作品発見等では、運営側が未発掘作品を一方的に押しつけ続けるのではなく、読者自身がその日の発見スタイルを選べる仕組みを導入候補とする。

候補：

未発掘作品を多め
自分の好みに近い作品
新作中心
完結作品中心
ランダム発掘

将来的には「安定寄り／冒険寄り」のように、人気・好み重視と未知作品重視の比率を読者自身が調整できる設計も検討する。

発見スタイル選択の目的は、作品露出の公平性を読者への強制によって実現するのではなく、「新しい作品を発掘したい読者」と「まだ十分に発見されていない作品」を自然に結びつけることである。

選択肢、推薦比率、表示方法等はβ版の実利用データから調整する。

## 4. NOVELIGHTの3原則

NOVELIGHTの機能・料金・アルゴリズム・運営を判断する際は、以下の基本思想を優先する。

① 評価される前の機会格差を減らす

知名度だけによって作品が読まれない状況を可能な限り減らす。

② 課金で評価そのものを買わせない

課金によって増やせるのは「発見される機会」であり、高評価・ランキング順位・作品そのものの価値ではない。

③ 作者と読者が長く小説を続けられる環境を作る

NOVELIGHTの最終目的は一時的なアクセス数ではなく、作者が書き続け、読者が読み続けられる環境を作ることである。

Freeの投稿可能作品数は2作品を正式上限とする。既存作品と新作、長編と短編等を同時に試せる余地を持たせ、無料利用でもNOVELIGHTを継続利用できる最低限の自由度を確保する。

投稿可能作品数は、Free 2作品、Standard 10作品、Premium 30作品とする。上限はUI表示だけではなくdatabase-sideのauthoritative ruleとして強制し、同時投稿等によって上限を越えられない構造を維持する。

Freeプラン独自価値の基本方針

Freeを単なる有料プランの劣化版にはしない。

有料契約を利用しない若年層を含め、Freeユーザーにも「NOVELIGHTを使う理由」が明確に存在する設計を目指す。

差別化候補の中心は以下とする。

新作初期露出

Free作品であっても、投稿しただけでほぼ誰の目にも触れない状態を可能な限り減らす。

NOVELIGHT側が一定量の初期表示機会を与え、「読まれること」ではなく「読者の前に出ること」までを支援する。

PV・高評価・ランキング順位を保証するものではない。

表示回数、対象作品、回数制限、再投稿対策等はβ版の実データと不正リスクを見て調整する。

露出バランス原則

新作初期露出等によって全作品へ最初の露出機会を与える一方、その後の露出は実際の読者反応を踏まえて調整することを基本原則とする。

知名度や既存フォロワー数だけで次の露出を決めず、作品ごとのクリック、第1話到達、第2話到達、LIGHT CHECK等の反応を参考にする。

基本循環の候補：

作品公開
→ 新作初期露出
→ 読者反応を計測
→ 良い反応なら追加露出
→ 反応が弱ければ露出を抑える
→ LIGHT ANALYTICS等の分析・改善導線で改善
→ 必要に応じて再テスト

目的は、「無名作品にも最初の機会を与えること」と「反応の弱い作品を読者へ延々と押しつけないこと」を両立し、作者側の公平性と読者体験を同時に守ることである。

ランキング順位や高評価を課金で買わせる仕組みにはせず、具体的な反応指標、追加露出量、再テスト条件等はβ版のデータから調整する。

公開チェック

新作初期露出等を、設定不足や単純な投稿ミスによって無駄にしないため、公開前の基本チェック機能を提供する。

候補：

あらすじが極端に不足していないか
ジャンルが設定されているか
タグが適切に設定されているか
表紙等の作品情報が不足していないか
第1話本文が正常に登録されているか
必要な年齢・内容警告が設定されているか
読みにくい表示・改行等の基本的な問題がないか

公開チェックは作品の面白さや実力を審査する機能にはしない。

目的は、「この作品は良い・悪い」とNOVELIGHTが判定することではなく、作者が読者の前へ作品を出す準備を整えることである。

Freeでも基本チェックを利用できる方向とし、β公開前は比較的軽量な簡易版から導入することを候補とする。

## 6. NOVELIGHTの責任範囲と課金効果の可視化

NOVELIGHTの仕事は、作品が読者に選ばれる結果そのものを保証することではなく、作品を読者の前まで公平に届ける機会を提供することである。

ただし、「届けたので、読まれないのは作者の責任」で終わらせない。露出と読書結果を数字で可視化し、作者が作品を改善するための材料まで提供する。

責任範囲は以下を基本とする。

NOVELIGHT

作品を読者の前まで届ける
特定作品だけが露出を独占しないよう分配する
露出と読書結果を数字で可視化する
作者へ改善材料を提供する

作者

読者に選ばれるタイトル、表紙、あらすじ、作品内容等を改善する
データを参考に作品を改善する

読者

NOVELIGHT側から特定の評価や行動を要求されず、自由に読みたい作品を選ぶ

作者が、

「980円・1,980円を払って何が変わったのか」

を理解できるようにする。有料プランの価値を曖昧な「優遇」だけにしない。

作者向け分析機能「LIGHT ANALYTICS」では、将来的に以下の流れを確認できるようにする。

インプレッション（作品表示回数）
→ CTR（作品ページへのクリック率）
→ 作品ページ閲覧
→ 第1話到達・読書開始
→ 第1話から第2話への継続率
→ 複数話読了
→ お気に入り等

加えて、「プランによる追加露出」、流入元、曜日・時間帯別PV等も可能な限り可視化する。

PVだけでなくインプレッションを重要指標として計測し、「どれだけ表示されたか」と「その後どれだけ読まれたか」を分離する。これにより、NOVELIGHTが十分に作品を届けられているか、タイトル・表紙・あらすじ等の入口に改善余地があるか、読書開始後の継続に改善余地があるかを切り分ける。

CTRが平均より低い場合等も作者を責めず、「作品は十分表示されていますが、作品ページへの移動率が低めです。タイトル・表紙・あらすじ等を見直すことで改善する可能性があります」のように改善材料を提示する。

ただし、NOVELIGHT全体平均・ジャンル平均との比較、平均より低い指標を用いた自動診断、高度な改善アドバイスは、βで十分なデータを蓄積し、精度と有用性を検証してから強化する。これらはβ公開を遅らせる必須要件にはしない。

NOVELIGHTでは、

露出する
→ 数字を見せる
→ 問題箇所・改善候補を示す
→ 作者が改善する
→ 再び露出する

という改善サイクルを作る。

β公開時点では、「Standardなら最低○○インプレッション保証」のような固定保証は行わない。読者数によって供給できる露出量が変わるため、まずは露出が少ない作品ほど次の露出機会を得やすくする相対的な分配を基本とする。

β版の実データからプラン別に安定して供給できるインプレッション量が分かってから、最低露出保証を導入するか再検討する。

従来の「初期100名まで」という人数上限は撤廃する。Founding Author資格は先行登録者数が100名を超えた後も打ち切らず、先行登録期間中に有効な先行登録を完了した作者を対象とする。

### 先行登録順番号

先行登録者については、先行登録が有効に成立した順番を恒久的な参加順番号として記録する。

番号は #001 から開始し、人数上限を設けず、#100 を超えても #101、#102 のように継続する。

先行登録順番号は記念性を持つ履歴として固定し、取消、後日のステータス変更、退会その他の理由で番号を詰め直さない。欠番が生じても既存番号を振り直さず、一度使用した番号を別の参加者へ再利用しない。

同一人物・同一先行登録について、再送信や重複操作によって複数の参加順番号が発行されないようにする。

先行登録時点では本アカウントが存在しない場合があるため、先行登録資格と参加順番号を先に保持し、その後の会員登録時に本人性を安全に確認して本アカウントへ紐付ける。会員登録や初投稿が遅れたことを理由に、先行登録時の番号を失わせたり後順位へ変更したりしない。

先行登録者の本人性確認は、**先行登録時のメールアドレスへ送付する本人専用の先行利用URL**を基本とする。メールアドレス文字列が一致するだけではFounding Author資格を本アカウントへ紐付けない。

先行利用URLは推測困難なBearer tokenを用い、raw tokenをDBへ保存せずhashのみを保持する。一度本アカウントへ使用されたtokenは再利用不可とし、有効期限・取消状態・送信済み状態をserver-sideで検証する。会員登録成功時はtokenを消費し、先行登録レコードへAuth userを明示的に紐付け、transport用tokenをAuth metadataへ残さない。

先行登録者が退会等によって本アカウントとの紐付けを失った後に再参加する場合も、メールアドレス一致だけで旧資格を復元せず、新しい本人専用URLを再発行して再確認する。Founding Authorの参加順番号そのものは再発行・振り直しせず、元の番号を維持する。

Founding Authorsには、後から購入・通常取得できない永久限定称号を付与する。正式表示は Founding Author #001 のように先行登録順番号を含む形式とする。SCOUT RECORDの称号コレクションへ保持し、公開プロフィールでは装備称号として選択した場合に表示する。

Founding Author資格と番号は、作品を最初に公開した順番では決めない。作品公開の早さによって先行登録者同士の番号が入れ替わる設計にはしない。

### β参加者の記念資格

先行登録者とは別に、NOVELIGHTのβ期間中に実際に会員登録して参加したユーザーについて、正式リリース後も判別できる「β参加者」資格を保存する。

β参加者資格には参加順番号を付けない。番号付きの参加順表示は先行登録者だけの特典とする。

β参加者には、永久限定称号 DAWNBOUND を付与する。後から対象者を再現できるよう、β期間中に資格取得時点を永続的に記録する。DAWNBOUNDは称号コレクションへ保持し、公開プロフィールでは装備称号として選択した場合に表示する。

先行登録者がβ期間中に会員登録して参加した場合は、番号付きFounding Author資格とβ参加者資格の両方を持つことができる。

運営・内部テスト・自動テスト等、実ユーザー参加として扱うべきでないアカウントは、Founding Authorおよびβ参加記念資格の対象数へ混入させない。

### ADMINでのカウント

運営はADMINから、少なくとも以下を確認できる状態を持つ。

- 有効な先行登録者数
- 先行登録順番号の最新到達番号
- 先行登録者のうち本アカウントへ紐付け済みの人数
- β参加者資格を取得した人数
- Founding Author限定称号対象者数
- DAWNBOUND対象者数

先行登録期間やβ期間が終了した後も、記念資格・参加順番号・資格取得時点を失わない。

## 15. ゲーミフィケーション

NOVELIGHTではゲーミフィケーションを積極的に利用する。

ただし、

### 読者側

読者側には比較的強く導入する。

中心は、

- LIGHT SEED
- SCOUT RECORD
- Scout XP
- Scout Level / Scout Rank
- 読者称号
- Scout Point
- 発掘実績

とする。

「作品を発掘する楽しさ自体をゲーム化する」ことを目指す。

Scout XPは読者としての成長・Level・Rankを示す非消費型の成長値とする。Scout Pointは将来利用できる補助報酬であり、両者を同一通貨にしない。XPを消費してAIを利用する設計にはしない。

Scout Pointは、単純なクリック回数・閲覧回数・回答回数を稼ぐための報酬にはしない。通常の有効読書、☆評価、有効コメント、LIGHT SEED送信そのものはScout XP側で評価し、Scout PointはLevel Up、発掘成功、NOVA予見、読者称号等の「成長・発掘・実績」を中心に付与する。

LIGHT CHECKを利用する場合も、回答回数だけでScout Pointを直接稼げる設計をβ版の既定としない。将来LIGHT CHECKへ独自報酬を追加する場合は、流し読み、無差別評価、機械回答を最適解にしない別途の正式仕様を必要とする。

基本循環は、

作品を探す
→ 実際に読む
→ 必要に応じて評価・コメント
→ LIGHT SEED
→ 作品が成長
→ 発掘成功
→ Scout XP / Scout Point / 読者称号 / SCOUT RECORD

とする。

SCOUT RECORDは正当な生涯実績を残す。一方、Scout Rankを作品評価の権力へ変換せず、高Rankユーザーの評価を作品Rankへ自動的に強く加算する仕組みは採用しない。

### 作者側

作者側は読者より穏やかに導入する。

作者称号は、初投稿、話数・文字数、完結、読者獲得、お気に入り、コメント、LIGHT SEED獲得、作品成長等、自然な創作活動の節目を中心にする。

連続投稿・短時間大量投稿等を称号獲得の最適解にせず、作者を過度に急かして作品品質を落とす設計にはしない。

作者称号には原則としてScout Pointを付与しない。Scout Pointは読者としての発掘活動を中心とする報酬として扱う。

具体条件・β暫定配点・限定称号との分離は第49章を正式基準とする。

ポイントは目的ではなく補助的報酬とする。

ただし「新しいから」という理由だけで採用しない。

自動化は目的ではなく、完成までの総時間・品質・安全性を改善するための手段である。

「自動化されている」という理由だけで効率的とは判断しない。既存の自動化についても、その自動化自体が最短・最小・再利用可能な方法になっているかを継続的に見直す。

新しい自動化・既存自動化を評価する際は、少なくとも以下を確認する。

変更範囲に応じた差分実行ができないか
独立した処理を並列化できないか
キャッシュ・成果物・環境構築結果を再利用できないか

安全性・データ保護のために必要な確認や重複を、効率化を理由に削っていないか

安全性・データ保護・本番変更等において、状態変化への再確認、承認後の再検証、バックアップ確認等に合理的な意味がある場合、その重複は無駄とは扱わない。

目的は作業することではない。NOVELIGHTを完成・成長させることである。

### ツール利用優先順位 / NLO First Policy

NOVELIGHTに関する作業では、原則として、NOVELIGHT運営・開発用に構築した専用ツール「NLO」を最優先の実行手段として扱う。

NLOは、従来「NOVELIGHT Commander」と呼んでいたNOVELIGHT専用ツールの正式名称とする。

NLOは一般のRemote Desktop Commanderとは別物であり、両者を混同しない。

対象は開発作業に限らず、以下を含む。

- NOVELIGHTの開発・修正・監査
- リポジトリ、ドキュメント、関連ファイルの確認
- Web小説の本文取得・読了確認
- 作品感想、作者向けDMの作成
- 競合サイト調査
- スクリプト実行
- NOVELIGHTの運営補助
- その他、NLOで実行可能な作業

#### 基本手順

1. NOVELIGHT関連作業を開始するときは、まずNLOで実行可能か確認する。
2. NLOの可用性は経路ごとに判定する。第一に直接NLO MCPが利用可能か確認し、直接NLO MCPがツール一覧へ露出していない、または応答しない場合は、GitHub Control Issue #797 のNLO GitHub Bridgeを確認する。Bridgeでは原則として `nlo_health` を使用し、旧版Bridgeで未対応の場合は `repo_snapshot` 等の安全な固定actionの成功応答を可用性証拠として扱う。
3. Remote Desktop CommanderはNLOとは別物である。Remote Desktop Commanderのdeviceが `offline` であっても、それだけを理由にNLOを `offline`、未接続、使用不能と判定してはならない。逆にRemote Desktop CommanderがonlineでもNLOの稼働証拠にはしない。
4. 直接NLO MCPまたはNLO GitHub Bridgeのいずれかが正常応答する場合、その利用可能な経路で実行できるNOVELIGHT作業についてNLOは利用可能と扱い、原則としてNLOを使用する。
5. 直接NLO MCPとNLO GitHub Bridgeの双方について、その作業に必要な機能が使えないことを確認した場合に限り、NLOがその作業では使用不能と判定して他の利用可能なツール・アプリへ切り替える。
6. 代替手段は、その作業に最も適したものを選択する。

例：

- Webページ読取・作品本文取得 → TinyFish等
- GitHub固有操作 → GitHub連携
- 一般Web調査 → Web検索系ツール
- PC・ローカル環境操作 → Remote Desktop Commander等
- その他 → 利用可能な最適な専用ツール

7. NLOが使用不能であることが明確な場合、同一作業中に無意味な再接続・再試行を繰り返さない。
8. NLOが再び利用可能になった後の新しいNOVELIGHT作業では、再度NLOを第一候補とする。

#### NLO可用性・自動復旧

NLOのOpenAI Secure MCP Tunnelは、通常運用でユーザーが毎回手動起動する前提にしない。

Windows環境では、以下を標準運用とする。

- Windowsログオン時にNLO Tunnelを自動起動する。
- Tunnelプロセスが回線瞬断、スリープ復帰、外部サービス一時障害等で終了した場合、自動再接続する。
- 短時間に連続失敗する場合はbounded backoffを入れ、無限高速再試行を避ける。
- CONTROL_PLANE_API_KEYは平文でTask引数・Git・チャットへ保存せず、Windows DPAPI等のOS保護ストレージを利用する。
- NLOがofflineになった場合は、単に再起動を繰り返すのではなく、Tunnelログ・Scheduled Task状態・最終接続時刻を確認して原因を切り分ける。
- 自動復旧機構が失敗している場合のみ、Remote Desktop Commanderその他の代替手段へ切り替える。

NLOの常時利用性は、NLO First Policyを実運用で成立させるための基盤とみなす。

#### 重要原則

「別ツールの方が使い慣れている」
「別ツールならすぐ実行できる」

という理由だけでNLOを飛ばしてはならない。

まずNLOの利用可否を確認し、利用できない場合にのみ代替手段へ移行する。

ただし、NLOでは実行できないことが仕様上明白な操作、または特定サービス専用API・専用連携でのみ安全に実行可能な操作については、最初からその専用ツールを利用してよい。

目的はNLOそのものを使うことではない。

NOVELIGHTの開発・運営作業を一貫した優先順位で、安全かつ効率的に完了させることである。

作業時間の可視化

NOVELIGHTに関する作業を開始する際は、原則として作業開始前に「全体の予想所要時間」と「主要工程ごとの予想所要時間」をユーザーへ示す。

見積もりは、例として「全体20〜30分／①確認2〜3分 → ②実装10〜15分 → ③テスト5〜10分 → ④反映3〜5分」のように、全体と各工程の両方が把握できる形で提示する。

短い作業であっても、複数工程に分かれる場合は可能な範囲で工程別の目安を示す。数秒単位の精密さを装わず、「約○分」「○〜○分」等の現実的な幅で見積もる。

1つの工程または外部処理が10分を超える見込みの場合は、その旨を開始前に明示し、ユーザーが待機する必要があるか、別の作業をしてよいか、次工程がその完了待ちになるかも併せて伝える。

CI、CodeQL、デプロイ、外部サービスの処理待ち等は、可能な限り「実作業時間」と「外部処理の待機時間」を分けて説明する。

作業中に当初見積もりを超える可能性が判明した場合は、判明した時点で理由、新しい予想所要時間、残り時間の目安を更新する。長時間化してから事後報告するのではなく、長引く可能性が見えた時点で共有する。

工程切替・再見積もりゲート

新しい主要工程へ入る直前には、その都度「10分以内か／10分超見込みか」を再判定する。最初の作業開始時に見積もり済みであっても、その後の工程へ自動的に引き継がない。

新しい工程が10分を超える見込みの場合は、最初のツール操作・編集・外部処理開始より前に、予想所要時間、外部待ち時間、ユーザーの待機要否、次工程がその完了待ちになるかを明示する。

当初10分以内と見積もった作業が、追加問題・再試行・調査範囲拡大等によって10分を超える見込みへ変わった場合は、その時点で作業時間を再報告する。

PRのmerge、主要CI・E2Eの完了、MASTER更新完了、デプロイ完了等は工程の明確な区切りとして扱う。区切り後はそのまま次工程へ進まず、「次工程確認 → 時間再見積もり → 必要な事前報告 → 着手」の順序を固定する。

報告・再見積もり・工程切替・チャット継続判定は、ユーザー承認ゲートではない。明示的な承認要件または合理的停止理由がない限り、ユーザーの「続けて」「はい」等を要求せず、そのまま次工程へ着手する。

承認ゲートの一本化（2026-09-21）

NOVELIGHTの通常開発工程では、ユーザーへ「承認」「コミット承認」「push承認」「PR作成承認」「マージ承認」等の個別承認を求めない。実装、検証、commit、push、PR作成、CI確認、レビュー対応、merge、Staging反映、read-only監査は、開始時に合意されたworkstreamの範囲内で連続して進める。

ユーザーへ明示的に求める承認は、原則として「本番承認」の1種類に統一する。本番承認が必要なのは、Production環境に状態変化を発生させる操作の直前とする。対象には、Production deployment、Production DB / Supabase migration、Production設定・Secret変更、Stripe / 課金設定、本番データの破壊的・不可逆的変更、その他live userへ直接影響するProduction mutationを含む。

mainへのmerge自体がVercelその他の仕組みによってProduction deploymentを自動的に開始する構成である場合、そのmergeをProduction mutationの開始点として扱う。この場合も「マージ承認」を別途求めず、merge直前に「本番承認」だけを求める。

本番承認前は、その本番変更に必要なコード、migration、PR、CI、Staging、rollback plan、検証証跡を準備してよいが、Production mutationそのものは開始しない。本番承認後は、承認対象の一連のProduction工程について、途中で新しい重大なリスク、承認範囲外の追加mutation、対象環境または内容の実質的変更が発生しない限り、同じ承認を細分化して再要求しない。

Productionのread-only確認、ログ確認、CI / CodeQL / Vercel status確認、監視、postcheck等、状態変更を伴わない確認は「本番承認」を必要としない。ただし、read-only確認の結果から新たなProduction mutationが必要になった場合は、そのmutation開始前に本番承認を得る。

GitHub branch protection、required checks、権限要求、外部サービスの確認画面等、システム上必須の安全手続きは維持する。ただし、それらを理由に不要なユーザー承認を追加で求めない。リポジトリ規則上、high-risk PR等に機械可読の承認コメントや専用Approval Ledger記録がHard Boundaryとして必須である場合も、ユーザーへ「マージ承認」「高リスク承認」等の別文言を追加で要求しない。ユーザーの「本番承認」を唯一の人間承認として受けた後、ChatGPTまたは自動化が、その本番承認を必要なGitHub承認コメント、Approval Ledger記録、challenge-bound形式等へ変換して投入する。対象head SHAやchallengeが変化して再承認が技術的に必要になった場合も、承認対象の実質的なProduction内容が変わっていない限り、既存の本番承認を再利用して機械側の承認証跡だけを更新し、ユーザーへ同じ承認を再要求しない。

チャット本番承認ブリッジ

ユーザーが、事前に示された対象・環境・変更内容を理解したうえで「本番承認」または同等の明示的な本番実行承認を行った場合、その1回を当該workstreamにおける唯一の人間承認として扱う。ユーザーへGitHub用の長い機械可読コメント、JSON、challenge、migration番号その他の技術的承認文を手作業で作成・コピー・貼り付けさせない。

本番承認を受けたChatGPTまたは自動化は、Production mutation開始前に、最新main、対象Environment、対象resource、pending migration、必要なread-only evidence、既存のApproval Ledgerをfreshに再確認する。その結果から、現在の固定workflow contractが要求するmain SHA、対象migration集合、一回限りのchallenge、operationその他の機械可読承認情報を自動生成し、OWNERとして認証された既接続GitHub経路から正式Approval Ledgerへ投入する。

Production Supabase migrationでは、原則としてactive Production Approval Ledgerと現在main上の承認workflow contractを使用し、最新main SHAと実際のpending migration集合を一致確認したうえで機械可読承認を生成する。ユーザーの「本番承認」を、別の「migration承認」「GitHubコメント承認」「実行承認」へ分割して再要求しない。

高リスクPRのmerge承認、Production migration承認その他で、承認後のmerge等によってfinal head SHA、main SHA、challengeその他の機械識別子が変化しても、ユーザーが承認した実質的なProduction変更範囲が同一であることをfresh evidenceで証明できる場合は、同じ人間の本番承認を基礎として機械証跡を再生成する。単にSHAやchallengeが変わったことだけを理由に、ユーザーへ本番承認を再入力させない。

ただし、承認後に新しいmigration、別Environment、別resource、追加の破壊的処理、課金・Secret変更その他の実質的なProduction変更が追加された場合は、元の本番承認の範囲外として新しい本番承認を必要とする。また、接続ツールがOWNER本人として機械可読承認を投入できない、対象範囲を一意に確定できない、最新状態が不明、または既存workflow contractと整合しない場合はfail closedし、安全ゲートを弱めたりbotをOWNER相当として偽装したりして承認を代替しない。

GitHub Actions、CodeQL、Vercel、Staging E2E、その他外部サービスの処理待ちも、ユーザーが作業全体の現在地を把握するための所要時間に含める。外部待ちであることは区別して説明するが、待ち時間であることを理由に時間報告の対象外にはしない。

各主要工程の完了時には、完了した工程と次工程の予想所要時間を可能な範囲で示し、ユーザーが現在地と残り時間を把握できる状態を維持する。

時間見積もりは約束された完了時刻ではなく、その時点の情報に基づく予測として扱う。ただし、予測であることを理由に説明を省略せず、見積もり精度は実績を踏まえて継続的に改善する。

MASTER-first Bootstrap

NOVELIGHTでツールを1回でも使う実行ターンでは、現在ターンの可視実行カードを最初に送信した後、最小限の読み取り専用Bootstrapとして最新 `main` を解決する。実行カードは新しいユーザーメッセージごとに必ず再発火する。

MASTERの正式基準は引き続き最新 `main` 上の `docs/NOVELIGHT-MASTER.md` とする。ただし、MASTER全文を毎ターン無条件にline 1から読み直すこと自体を安全性の目的にしない。安全上必要なのは、current main上の正式内容が、過去に完全読了した内容と同一かを機械的に確認することである。

#### Content-addressed MASTER reuse

初回、または再利用条件を満たさない場合は、latest main上のMASTERをline 1からconfirmed EOFまで完全読了し、`MASTER_READ_COMPLETE` を成立させる。 この初回成立では、同じターン内でlatest main解決とMASTER全文読了を完了し、途中の別project-state観測を読了証跡へ混入させない。ツール応答にtruncated、途中切れ、未解決rangeがある場合は、そのrangeを細分化して再取得し、欠落が解消するまで通常作業へ進まない。

以後の実行ターンでは、実行カード送信後に必ずlatest mainをfreshに解決し、少なくともMASTER、`docs/WORK-EXECUTION-PREFLIGHT.md`、`docs/AUTOMATION-CONTINUATION-GATE.md` のcurrent blob SHAまたは内容digestを確認する。

次をすべて満たす場合、以前の完全読了証跡を `MASTER_CONTENT_REUSE` として再利用し、MASTER全文再読を省略してよい。

- 再利用元がline 1からconfirmed EOFまで欠落なく読了済みである
- current main上のMASTER blob / 内容digestが、その完全読了時と完全一致する
- PreflightとContinuation Gateのblob / 内容digestも、最後に確認した正式基準から変化していない
- 今回の作業スコープが、既に確認済みの安全境界内にある
- MASTER、Preflight、Continuation Gateそのものの変更作業ではない
- Auth、RLS、Secret、Stripe / 課金、Production DB、破壊的操作その他の高リスク境界へ新たに拡大していない

latest mainが別作業によって進んだことだけでは、MASTER内容が同一なら全文読了証跡を失効させない。current mainのMASTER blob / digestが再利用元と一致することをfreshに確認し、関連ファイルの競合・差分だけを確認して継続する。

新しいユーザーメッセージを受けた時点で**前ターンの可視実行カードは必ず失効する**。一方、完全読了済みMASTERとcurrent mainの内容同一性が機械的に証明できる場合、MASTER内容証跡まで捨てて全文再読する必要はない。会話上の記憶だけを根拠に再利用してはならず、必ずcurrent main上のblob / digest一致を確認する。

次の場合は `MASTER_CONTENT_REUSE` を使わず、latest main上のMASTERをline 1からconfirmed EOFまで再読する。

- MASTER blob / 内容digestが変化した
- PreflightまたはContinuation Gateが変更された
- MASTERまたは安全ゲート・承認境界を変更するworkstream
- Auth、RLS、Secret、Stripe / 課金、Production DB、破壊的migration等の高リスクworkstreamへ新たに入る
- 完全読了証跡が見つからない、coverageが不明、またはtruncationが未解決
- ユーザーが明示的にMASTER全文再読を要求した

Runtime Gateへ証跡を渡す場合は、current mainをfreshに解決したうえで、再利用元と同一であることを確認したMASTER digest / EOF coverageをcurrent mainへ再bindしてよい。これを「記憶で運用する」こととは扱わない。

#### SCOUT称号アートワーク反復実装 Fast Path

SCOUT RECORDの称号画像を追加する反復作業は、以下の条件を満たす場合、通常の機能開発より短い専用Fast Pathで処理する。

対象条件：

- badge catalog、badge_id、称号名、獲得条件が既存仕様・DBに存在する
- 画像デザインは完成・承認済みで、新規生成・再デザインを行わない
- 作業対象は称号画像asset、表示mapping、一覧・詳細モーダル、fallback、関連テストに限定される
- Supabase migration、Auth、RLS、Secret、Stripe、Production DB mutationを伴わない
- Founding Author等の限定称号と、画像未登録称号のglyph fallbackを維持する

Fast Pathの標準手順は次とする。

1. **Bootstrapを短縮する。** 可視実行カード → fresh latest main → MASTER / Preflight / Continuation Gateのblob確認を行い、`MASTER_CONTENT_REUSE` 条件を満たせば全文再読を行わない。SCOUT仕様は第49章と対象差分だけを確認する。
2. **NLO確認はbatch単位で1回を基本とする。** 直接NLOまたはIssue #797の `nlo_health` が成功したら、同一badge batch中に無意味なhealth再確認を繰り返さない。NLO action失敗、接続状態変化、長時間中断等があった場合だけ再確認する。
3. **画像を1枚ずつ処理しない。** 完成済み個別画像がある場合はbatchでまとめて取得・materializeする。元画像が取得不能でcanonical spriteからの機械的切り出しが許可された場合だけ、絵柄を変えずbatch切り出しする。ChatGPT画像生成・画像編集は、現在のユーザー指示で明示解除されていない限り使用しない。
4. **canonical pathを固定する。** SCOUT称号画像は原則 `assets/scout-badges/<badge_id>.png` とし、同一badge_idを別名・別場所へ重複登録しない。
5. **batch validationを先に1回で行う。** 件数、canonical順、badge_id重複、ファイル名、PNG signature、期待寸法、欠損、余剰、0-byte、mapping対象を一括検証する。現行標準は256×256 PNGとし、将来別仕様を採用する場合はbatch開始時に期待寸法を固定する。
6. **登録も一括化する。** binary assetはbounded parallelでblob化し、可能な限り1つのGit tree / commitへまとめる。画像ごとにbranch、commit、PR、CIを分けない。
7. **表示mappingは1か所を正本にする。** 同じ `badge_id → asset path` を一覧と詳細モーダルが共有し、表示箇所ごとの二重mappingを作らない。画像未登録時は既存glyph fallbackへ戻す。
8. **旧方式テストをPR前に処理する。** sprite、旧path、旧class等の過去前提を検索し、今回の正式方式と衝突するテストは同じbranch内で先に更新する。Prettier / format check、専用Node test、静的asset検証をPR作成前に通し、CIで初めて旧前提やformat errorを発見する運用を避ける。
9. **CIは完成batchに対して1回を基本とする。** branch上のbatchが揃ってからPRを作成し、CI / CodeQL / desktop / mobile / Vercel Previewをまとめて確認する。失敗時は原因箇所だけを修正し、不要な全工程や画像処理をやり直さない。
10. **main追従で全作業を再起動しない。** 作業中にmainが進んだ場合、MASTER / Preflight / Gateのhashと対象ファイル競合を確認する。無関係な変更なら作業を維持し、最終CI前またはmerge前に1回だけlatest mainへ同期する。対象ファイルや正式基準が競合した場合だけ再評価する。
11. **Preview目視を必要最小限にする。** 全badge_idのpath・asset existence・寸法・mappingは機械検証し、desktop / mobileのレイアウトは自動E2Eで確認する。同じレイアウトへ画像だけ追加する反復batchでは、人間が30枚・50枚を毎回1枚ずつ目視確認することを必須にしない。代表サンプルと異常検知結果を目視し、mapping不一致・表示崩れが疑われる場合に範囲を広げる。
12. **Production境界だけは維持する。** main mergeがProduction deployを開始する構成では、必要な本番承認をmerge直前にのみ扱う。安全な準備工程で「はい」「続けて」を要求しない。

Fast Pathの品質条件：

- batch内の全badge_idが期待assetへ一意に対応する
- 一覧カードと詳細モーダルで同じ画像を使う
- 獲得済み / 未獲得、Reader / Author / Limited、difficulty filterを壊さない
- Founding Author番号・画像表示を回帰させない
- 画像未登録称号は404を大量発生させずglyph fallbackを維持する
- Console errorなし
- desktop / mobile自動検証PASS
- 旧sprite / 廃止pathへの意図しない参照なし

完成済み個別画像が揃っており、表示ロジックの新設が不要な通常batchでは、**実作業の目標を5〜10分程度＋外部CI / Preview待機**とする。元画像探索、spriteからの復元、layout変更、既存不具合修正が必要な場合はFast Path外の追加作業として分離し、早い段階で再見積もりする。

このFast Pathの目的は検証を減らすことではなく、同じ安全確認・同じファイル処理・同じCIを何度も繰り返す無駄をなくすことである。

画像ツール既定拒否

NOVELIGHTでは、ChatGPT側の画像生成・画像編集ツールを新しいユーザーメッセージごとに既定でロックする。画像やスクリーンショットの添付、デザイン相談、可否確認、改善案、過去ターンの画像指示、単なる「はい」「続けて」等から画像実行を推測してはならない。

ChatGPT側の画像生成・画像編集を実行するには、現在のユーザーメッセージそのものに、ChatGPT側画像ツールのロックを明示的に解除・再有効化する指示と、画像を実際に生成・編集する明示指示の両方が必要である。どちらか一方でも確認できない場合は画像ツールを候補から除外し、テキストのみで対応する。ノクター等により強い個別ロックがある場合は、その個別ロックを優先する。

NOVELIGHTの実作業では、資料確認、GitHub確認、参照素材の整理、方針設計、プロンプト作成等の準備工程のみを完了した状態で、作業そのものが完了したかのように応答を終了しない。

途中停止を行うのは、原則として、外部サービス・ツールのエラー等により物理的に続行できない場合、必要な権限・素材・情報がなく合理的な代替手段もない場合、指示間に重大な矛盾がありそのまま進めると成果物を壊す可能性が高い場合、ユーザーの判断なしには重要な分岐を安全に決定できない場合、安全性・法務・データ保護等の理由で停止が必要な場合に限る。

応答を終了する前に、今回の最終ゴールに実際に到達したか、準備工程だけで止まっていないか、ユーザーが依頼した本体作業へ入っているか、今返答する必要のある合理的な停止理由が存在するかを確認する。

目的は途中報告の回数を減らすことではなく、準備作業を成果と取り違え、ユーザーが再度「続きをやって」と指示しなければならない状態を防ぐことである。

チャット切替・引き継ぎ

NOVELIGHTの作業チャットが長くなり、応答速度、参照効率、作業精度、操作の分かりやすさ等が低下する可能性がある場合、ChatGPTはユーザーから聞かれるまで待たず、キリの良い工程で新しいチャットへの切替を提案する。

チャット継続判定ゲート

NOVELIGHTの主要工程が完了した時点で、ChatGPTは必ず「現在のチャットを継続するか、新しいチャットへ切り替えるか」を判定する。ユーザーから切替時期を質問されるまで、この判定を先送りしない。

特に、PRのmerge完了、大規模テスト・E2Eの完了、MASTER更新完了、復旧作業の完了、1つの開発・企画・制作テーマの完了等、明確な区切りではチャット継続判定を省略しない。

判定時は、チャットの長さだけでなく、参照対象となるPR・Workflow Run・ブランチ・決定事項の増加、複数テーマの混在、修正や再試行の蓄積、応答速度・参照効率・作業精度・操作の分かりやすさへの影響を総合して判断する。

チャット切替が有利と判断した場合は、次の主要作業へ進む前にChatGPT側から切替を提案する。その際は、現在の工程が安全に完了していることを明示し、次チャットへそのまま貼り付けられる引き継ぎ指示文を同時に提示する。

現在のチャットを継続した方が文脈保持・作業効率上有利な場合は、そのまま継続してよい。ただし「判定そのもの」を省略してはならない。

主要工程の完了報告では、原則として「完了した内容」「次に行う作業」「チャット継続判定」を一連の終了確認として扱う。切替推奨の場合は必ずユーザーから聞かれる前に伝える。

ただし、実行中の重要処理、未確認の本番変更、復旧途中の作業等を中断させる形では切り替えない。現在の工程が完了しているか、切り替えて安全な状態かを明示してから提案する。

チャット切替を提案する際は、ユーザーが長い経緯を自分で書き直さなくて済むよう、次の新しいチャットへそのまま貼り付けられる短い引き継ぎ指示文を必ず作成する。

引き継ぎ指示文には、少なくとも以下を含める。

現在の作業目的
直前までに完了した重要事項
次に行うべき作業
関係するPR、Workflow Run、ブランチ、画面操作等がある場合はその現在地
作業開始時に最新mainとmain上の `docs/NOVELIGHT-MASTER.md` を再取得し、それを唯一の正式な基準とする指示
全体と主要工程ごとの予想所要時間を先に示す指示

新しいチャットでは、前チャットの要約・記憶だけを正式な状態として扱わず、開発作業ではGitHubの最新main、最新MASTER、必要なPR・Workflow等を実際に再確認してから続行する。

X・マーケティング・デザイン・企画等についても、必要な最新決定事項と次の目的を短く引き継ぎ、ユーザーに過去の会話を再説明させることを可能な限り避ける。

目的はチャットを細かく分けることではなく、長時間作業でも文脈の正確性、作業速度、引き継ぎの容易さを維持することである。

## 20. 開発基本方針

開発では最新のAI開発手法・自動化を積極的に利用する。

Codex等を主な実装手段として利用し、認証・課金・RLS・セキュリティ等の重要実装では必要に応じてClaude等の別AIによる独立レビューも利用する。

VS Code、GitHubその他のツールも含め、その時点で最も効率的な環境を採用する。

将来さらに優れた方法が登場した場合は、現在の環境に固執しない。

最速だけを目的にせず、完成までの総時間・品質・安全性を最適化する。

軽微な不整合・品質問題の扱い

動作に直接影響しない文言のズレ、警告、CI設定の不整合、不要なエラー表示、テスト結果と説明文の食い違い等についても、発見した問題を放置して技術的負債として蓄積させない。

安全に短時間で修正・検証できるものは、その場で修正することを基本とする。機能上は動いていることだけを理由に、誤解を生む表示、不要な警告、将来の障害要因となる設定不整合を残さない。

ただし、軽微な修正から大規模な改修へ発展する場合は別タスクとして切り分け、影響範囲・優先度・β公開への影響を再評価する。細部を直し続けることによって、β公開に必要な主要作業を不必要に遅らせない。

失敗・不具合の再発防止

不具合や作業失敗が発生した場合は、個別事象だけを直して終了せず、「単発の偶発事象か」「同種の作業で再発し得る構造的な問題か」を確認する。

再発し得る構造的な問題である場合は、可能な範囲で回帰テスト、Preflight、自動検査、Contract Test、CIゲート、ログ強化、監視、手順改善等のいずれかへ落とし込み、同じ種類の失敗を人間の注意力だけで防ぐ設計にしない。

同種の失敗が複数回発生した場合、または一度の失敗でも認証・課金・RLS・セキュリティ・データ保護・デプロイ等の重要領域に関わる場合は、再発防止策の検討を原則として必須とする。

外部サービスの実挙動確認

Stripe、Supabase、Vercel、GitHubその他の外部サービスについて、重要な状態遷移やAPI挙動を推測・固定観念だけで決めない。Sandbox、Test環境、公式仕様、実際のAPI応答等を使って確認し、実挙動と実装の前提が一致しているか検証する。

外部サービスが同じ意味を複数のフィールド・状態表現で返し得る場合は、必要な意味条件を安全に判定し、観測した非機密の重要状態をテストログやSummary等へ可能な範囲で残す。

E2Eや成功Summaryは、実際の合格条件より強い事実を断定しない。テスト本体が複数の正常表現を許容する場合、人間向けの表示・ログも同じ意味条件と整合させる。

PR・CI・merge前整合確認

PRをmergeする前は、必要に応じて最新mainとの整合、必須チェックの存在、CI・CodeQL等の発火条件、ブランチ保護・Repository Rulesが要求するチェックとWorkflow側のpaths条件等が矛盾していないかを確認する。

「必須チェックなのに変更内容によってWorkflow自体が起動しない」状態を作らない。新しい必須ゲートやWorkflow条件を追加・変更する場合は、対象となる主要な変更パターンでチェックが生成されることも検証する。

同じ確認を繰り返す必要がある場合は、Merge Readiness Preflight等として可能な範囲で自動化し、merge直前になって初めて不整合が判明する状況を減らす。

再発防止のための改善自体が大規模化する場合は、現在の修正を安全に完了させたうえで別タスクとして明示的に残し、重要度に応じて優先順位を付ける。再発防止を理由に無制限にスコープを拡大しない一方、後回しを理由に問題そのものを忘れない。

## 24. 新機能・ロードマップ管理

新しいアイデアは以下に分類する。

A：今すぐ必要

バグ、セキュリティ、重大UX、根幹機能等。

インプレッション、CTR、読書開始、第1話→第2話継続率、お気に入り等の基本ファネルの計測と基本的な可視化は、NOVELIGHTが作品を読者へ届けていることを証明し、課金価値と「評価される前の機会格差を減らす」という基本思想を検証する仕組みである。この範囲をβ公開前に必要なAとして扱う。全体・ジャンル平均との比較、自動診断、高度な改善アドバイスはAの必須範囲に含めず、βのデータ蓄積後に強化する。

B：次に実装する価値が高い

継続率・発掘体験・差別化等を大きく改善するもの。

C：面白いが今は不要

アイデアとして保存し、将来再評価する。

## 35. MASTER管理・正本保護原則

NOVELIGHT MASTERは、NOVELIGHTの戦略・企画・開発・運営における唯一の正式な正本（Single Source of Truth）として扱う。

GitHubの `docs/NOVELIGHT-MASTER.md` を正式なMASTERとし、別ファイル・過去バックアップ・チャット内のコピーを「最新版」として並存させない。バックアップは復旧用の履歴であり、正本ではない。

MASTERを更新する場合は、必ずその時点の正本最新版を全文確認したうえで、原則として必要箇所への差分追記・差分修正として行う。

MASTER全体を古い版や別コピーから再生成・置換する方法を通常の更新手段として使用しない。

既存の方針・機能・決定事項を削除または大幅変更する場合は、ユーザーがその変更を明確に決定した場合に限る。新しい方針を追加することを理由に、無関係な既存方針を消してはならない。

更新時は必ず、

更新前の正本を取得する
変更対象と既存内容の矛盾を確認する
必要最小限の差分を適用する
更新前後のdiffを確認する
意図しない削除・章欠落・大幅な文書縮小がないことを確認する
復旧可能な履歴を残す

という手順を取る。

特に「既存内容を維持したまま追記する」更新では、削除行が発生した場合は原則として異常として扱い、その削除が意図した変更かを確認する。

MASTER変更は自動保護ゲートの対象とし、章の欠落、重要原則の消失、異常な文書縮小等をCIで検知する。自動検査を通過したことだけで内容の正しさを保証せず、人間・AIによる差分確認と併用する。

MASTERの復旧が必要になった場合は、単一の古い版をそのまま採用せず、正本のGit履歴、保存済みバックアップ、その後に決定された事項を時系列で照合し、欠落・巻き戻しがないことを確認して復旧する。

MASTER管理の目的は文書を更新することではない。NOVELIGHTの意思決定履歴と一貫性を失わず、プロジェクト全体が常に同じ最新方針を参照できる状態を守ることである。

## 36. ホーム画面・作品発見UI方針

ホーム画面の最上位目的は、NOVELIGHTというサービスの説明を増やすことではなく、読者が作品を発見し、実際に作品を開くことである。

ホームを企業サイト・運営情報ページのように情報過多にせず、読者向けUIはシンプルに保つ。一方、裏側の露出・推薦・計測ロジックは、公平性と課金価値を両立するため必要な複雑さを持たせてよい。

主要なおすすめ・発見棚は、選択肢を大量に並べるのではなく少数の作品へ絞る。基本目安はデスクトップ6作品とし、モバイルではスクロール負荷・選択負荷を抑えるため4作品程度＋「もっと見る」等の導線を基本候補とする。画面上で実際に表示されていないカードを、単に裏側で割り当てたことだけを理由に露出実績として数えない。

β初期の作品棚は、原則として以下の順に育てる。

1. あなたへのおすすめ・発見棚
2. 新着作品
3. LIGHT SEEDで発掘中
4. 将来的な人気上昇中等の補助棚

LIGHT SEEDで発掘中は、意味のあるLIGHT SEED利用・データが十分に蓄積してから本格表示する。カタログ・利用データが少ない時期に棚を無理に増やし、同じ作品の反復によってサービス規模を小さく見せることは避ける。

おすすめ順は、ページ更新のたびに全作品が入れ替わる純粋ランダムにはしない。短時間の再読込では一定の安定性を持たせ、時間経過、再訪、閲覧履歴等に応じて徐々に作品が入れ替わる制御されたローテーションを基本とする。

推薦・露出では、以下を独立した6つの表示棚としてランダムに並べ替えるのではなく、作品ごとの選出・順序を決める複数の条件として組み合わせる。

新作の初期露出
Freeの発見機会
Standardの追加露出
Premiumの追加露出
その読者が最近見ていない作品の優先
同じ作者への露出集中の抑制

Free作品にも実質的な発見機会を残す。Standard・Premiumは追加露出・選出確率・追加機会等によって有料価値を持たせるが、有料であることだけを理由に常に先頭へ固定しない。新作、未閲覧、露出不足等の条件が強いFree作品が、既に十分露出された有料作品より優先される場合を許容する。

基本バランスは、

「公平性 × プランによる追加露出 × ローテーション」

とする。

課金による追加露出は内部では正確に割当・計測する一方、読者向けホームでは「広告作品」「課金枠」が主役に見える表示を避け、自然な作品発見体験を優先する。ただし、料金ページ、露出方法の説明、作者向け分析等では、プランによる追加露出の存在と基本原則を透明に説明する。

本方針は新作初期露出、露出バランス原則、Freeでも良作が伸びられる原則、「課金で評価そのものを買わせない」という3原則と一体で運用する。

ホームには、お知らせ本文、問い合わせフォーム、FAQ、メンテナンス情報等の運営情報を安易に追加しない。ホームは作品発見を主役とし、運営・サポート情報は専用導線へ分離する。

## 37. お知らせ・お問い合わせとADMIN運営ハブ方針

公開サイトの運営情報・サポート情報は、作品発見を主役とするホーム画面から分離する。

公開サイトには、フッター等へ「お知らせ・お問い合わせ」のような簡潔な入口を設け、その専用画面内で、運営からの公式お知らせの閲覧とユーザーからのお問い合わせ送信を完結できる構成を基本とする。

既存のお問い合わせについては、安全な送信経路、入力検証、スパム・濫用対策、個人情報保護を維持する。公開ユーザーが問い合わせを送信できることと、問い合わせの生データを読めることは分離し、メールアドレス、本文その他の非公開情報を一般ユーザーへ公開しない。

公式お知らせはADMINから管理する。β初期の管理機能は、タイトル、本文、種別、状態、公開日時等を扱える文字中心の軽量な仕組みを基本とし、新規作成・編集・下書き・公開・アーカイブのライフサイクルを管理できるようにする。

ADMINで公開したお知らせは公開サイトのお知らせ画面へ反映する。β初期から画像付きの高度CMS、複雑な予約配信その他の重い出版機能を必須要件にはしない。

お問い合わせは逆方向に、

公開サイトの問い合わせフォーム
→ 安全な問い合わせ保存経路
→ ADMINの運営画面

へ集約する。

ADMINでは、既存の問い合わせ状態管理に沿って、少なくとも new → reviewing → resolved 相当の対応状況を確認・更新できるようにする。

問い合わせの返信先メールアドレスや本文等の機微な詳細は、ADMINの通常概要レスポンスへ混在させない。認証済みかつAllowlistで許可された管理者が詳細を開いた場合にのみ、サーバー側の管理者経路を通じて必要な情報を取得・表示する。通常ユーザーや公開クライアントから取得できる構造にはしない。

ADMINは、単なる数値ダッシュボードではなく、少人数＋AI・自動化でNOVELIGHTを運営するための「運営ハブ／司令塔」へ段階的に育てる。

少なくともADMINの運営概要では、未処理のお問い合わせ、未処理の通報、公開中のお知らせ等、現在対応が必要な項目を一目で把握し、該当管理画面へ移動できる状態を目指す。

長期的な運営原則は、

「NOVELIGHTで今何に対応すべきか確認したい場合、まずADMINを開けば分かる」

状態を作ることである。

ただし今回の初期方針では、ADMIN内からのメール返信送信システムまでを必須範囲にしない。まず、受信する、未対応を把握する、内容を確認する、対応中・対応済みを管理する、という運営フローを確実に完成させる。メール送信基盤等は必要性と安全性を別途評価して追加する。

本方針は、コミュニケーション・透明性、個人情報・権限管理、少人数＋AI・自動化の運営原則、ADMINの認証・Allowlist境界と一体で運用する。

## 38. SCOUT RECORD・作品成長Rank・LIGHT SEED正式仕様

本章は、作品成長Rank、LIGHT SEED、発掘判定、Scout XP、Scout Level、有効読書および発掘報酬の基礎仕様を定める。2026年9月21日にSCOUT RECORD本実装方針を更新し、Scout Point、読者称号、作者称号、β版Lv.30上限、表示範囲、Ledger、不正対応、KPI、UIおよび未確定事項は第49章を最新の正式仕様とする。旧記述の「SCOUT EXP」はScout XPと同じ成長値を指す。

本章の具体仕様は、第3章、第15章、第34章および本章更新前のSCOUT・LIGHT SEED・作品成長Rankに関する暫定記述を更新する。内容が矛盾する場合は、本章の具体仕様を優先する。

### 基本原則

作品成長Rankは、作品が実際に読まれ、支持された結果を示す。

LIGHT SEEDは、読者が「もっと知られてほしい」と判断した作品へ発掘・推薦の意思を残し、その作品を他の読者が認知する機会を増やす仕組みとする。

LIGHT SEED自体は、作品成長Rank、PV、お気に入り、☆評価その他のRank算定値へ直接加点しない。

SCOUT制度では、単にSEEDを多く配った人ではなく、作品を読み、早い段階で将来伸びる作品を見つけ、作者へ評価・反応を返した人が高く成長できる構造を目指す。

### 作品成長Rankの正式名称

作品には6段階の作品成長Rankを設ける。

Rank 1：EMBER
Rank 2：SPARK
Rank 3：GLOW
Rank 4：BEACON
Rank 5：STAR
Rank 6：NOVA

UIでは原則として数字と名称を併記する。

EMBERは作品品質が低いことを意味せず、「まだ十分に発見されていない小さな光」を表す。

### Rank算定の二重条件

各Rankは、以下の両方を満たして成立する。

1. Rankごとの最低絶対水準を満たすこと
2. アクティブ作品全体の相対分布上、そのRank帯へ入ること

相対割合は以下を基本とする。

Rank 1：下位40%
Rank 2：次の30%
Rank 3：次の15%
Rank 4：次の10%
Rank 5：次の4%
Rank 6：上位1%

すなわち、Rank 1〜2が約70%、Rank 3〜4が約25%、Rank 5〜6が約5%となる構成を基本とする。

### β開始時の最低絶対水準

β開始時は以下を初期値とする。

Rank 1 EMBER：公開作品であること。

Rank 2 SPARK：有効読者数50以上、お気に入り2以上、☆評価人数2人以上、☆平均3.0以上。

Rank 3 GLOW：有効読者数200以上、お気に入り8以上、☆評価人数5人以上、☆平均3.3以上。

Rank 4 BEACON：有効読者数800以上、お気に入り30以上、☆評価人数15人以上、☆平均3.5以上。

Rank 5 STAR：有効読者数3,000以上、お気に入り100以上、☆評価人数50人以上、☆平均3.7以上。

Rank 6 NOVA：有効読者数10,000以上、お気に入り300以上、☆評価人数150人以上、☆平均4.0以上。

作品成長Rankに用いる「有効読者数」は、第38章の有効読書判定を満たした読者を作品単位で集計した値とする。同一読者が同一作品内で複数エピソードの有効読書を成立させても、作品Rank・公開ランキング上は1読者として数える。既存の `valid_read_events` は判定証拠のSource of Truthとして維持し、集計時に `reader_id` を作品単位で重複排除する。

通常のPVは作者向け分析・利用状況把握・異常検知等の参考値として継続して計測してよいが、匿名visitor tokenの変更等による水増しが作品Rank・公開ランキングへ直接反映されないよう、作品成長Rankの最低絶対水準および内部スコアには直接使用しない。β版の一般作品検索でもraw PVによる公開並び替えは提供せず、PVは参考表示・分析用途に限定する。

これらはβ初期の運用値であり、βの実データから調整可能とする。

### Rank内部スコア

β初期のRank内部スコアは、有効読者数20%、お気に入り35%、☆関連指標45%を基本とする。

有効読者数・お気に入り・☆関連指標の生の数値をそのまま加算しない。サービス規模の拡大によって特定指標の桁が変わっても重みが崩れにくいよう、各作品をアクティブ作品母集団内で比較し、各指標を0〜100のパーセンタイルスコアへ変換してから加重合成する。

読書量スコアは、アクティブ作品内の有効読者数パーセンタイルとする。

お気に入りスコアは、アクティブ作品内のお気に入り数パーセンタイルとする。

☆関連スコアは、単純な平均☆だけではなく、ベイズ補正した☆平均と☆評価人数を組み合わせる。

補正☆平均は、以下を基本式とする。

補正☆平均 = (n / (n + m)) × R + (m / (n + m)) × C

R：その作品の平均☆
n：その作品の☆評価人数
C：NOVELIGHT全体の有効☆評価から算出する基準平均
m：事前信頼強度

β初期の事前信頼強度mは10とする。評価人数が少ない作品ほど全体平均Cへ寄せ、評価人数が増えるほど作品自身の平均☆Rを強く反映する。mはβ実データから調整可能とする。

補正☆平均についてもアクティブ作品内で0〜100のパーセンタイルスコアへ変換する。☆評価人数も同様に0〜100のパーセンタイルスコアへ変換する。

☆関連スコアは、

補正☆平均パーセンタイル × 0.75
＋ ☆評価人数パーセンタイル × 0.25

とする。

最終的な作品総合スコアは、

作品総合スコア = 有効読者数パーセンタイル × 0.20
＋ お気に入りパーセンタイル × 0.35
＋ ☆関連スコア × 0.45

とする。

展開すると、総合スコアに対する実質的な比率は、

有効読者数：20%
お気に入り：35%
ベイズ補正☆平均：33.75%
☆評価人数：11.25%

となる。

作品総合スコアが高いだけでは上位Rankへ昇格できない。各Rankの最低有効読者数、最低お気に入り数、最低☆評価人数、最低☆平均の絶対条件をすべて満たしたうえで、アクティブ作品全体の相対割合条件を満たす必要がある。

パーセンタイルの同順位処理、丸め精度その他の実装詳細は、同じ入力に対して決定論的かつ再現可能であることを必須とし、β実データから必要に応じて調整する。ただし、生値の単純加算へ戻す変更は行わず、相対的な0〜100正規化を基本構造として維持する。

### Rank昇格の安定判定

一時的なアクセス集中や不自然な操作だけでRankが瞬間的に上がりにくいよう、β初期は以下の継続条件を置く。

Rank 2：24時間
Rank 3：24時間
Rank 4：48時間
Rank 5：72時間
Rank 6：7日間

必要に応じてβ実データから調整する。

### 作品の休眠と降格

未完結作品は、最後のエピソード更新から30日で休眠扱いとし、アクティブ作品の相対割合計算から除外する。ただし30日時点ではRankを即時降格させない。

最後のエピソード更新から60日で現在Rankを1段階降格する。

その後も更新がない場合は、さらに60日ごとに1 Rankずつ降格する。下限はRank 1 EMBERとする。

更新を再開した作品は再びアクティブ母集団へ参加するが、休眠前のRankを自動返却しない。現在のPV・お気に入り・☆および相対条件を再び満たし、通常のRank判定によって実力で取り戻す。

過去最高Rankは履歴として保持する。

未完結Rank 6についても通常の休眠・降格ルールを適用し、旧暫定仕様の永久的なRank 6保護は採用しない。

### 完結作品とFINAL RANK

完結作品は通常の休眠・降格対象外とする。

完結直後にはRankを即固定せず、完結後30日間の読者反応を含めたうえでFINAL RANKを確定する。

正式表示名称は「FINAL RANK」とする。

最初の「連載中 → 完結」は、生涯2回の状態切替制限へ含めない。

最初の完結後の「完結 → 連載中」を1回目、その後の「連載中 → 完結」を2回目として扱う。2回使用後は原則変更不可とし、重大な誤操作等は運営判断で例外対応できる。

完結を解除した場合、過去FINAL RANKは履歴として保持する。作者本人には表示するが、読者にはデフォルト非表示とする。作者は任意で過去FINAL RANKを公開できる。

再完結した場合は新しいFINAL RANKを現在のFINAL RANKとして扱う。

### LIGHT SEEDの種類と月間配布

LIGHT SEEDは以下の3種類とする。

GOLD LIGHT SEED（金のLIGHT SEED）
SILVER LIGHT SEED（銀のLIGHT SEED）
BRONZE LIGHT SEED（銅のLIGHT SEED）

各ユーザーへ毎月1日に以下を付与する。

GOLD：6個
SILVER：3個
BRONZE：2個

合計11個。

未使用分は翌月へ繰り越さない。

月途中の新規登録者にも、その月のGOLD 6、SILVER 3、BRONZE 2を全量付与する。翌月1日には通常どおり新しい月間分を付与する。

### LIGHT SEED送信条件

LIGHT SEEDを送るには、対象作品について1エピソード以上の有効読書が成立していることを必須とする。

自分自身の作品へは送信できない。

下書き・非公開作品へは送信できない。

完結作品へは送信可能とする。

Rank 1〜6のすべての公開作品へ送信可能とし、Rank 6 NOVAにも送信できる。

LIGHT SEED種類は作品Rankによって自動決定せず、ユーザーが保有するGOLD・SILVER・BRONZEの中から選択して送信する。

### 同一作品への制限

1ユーザーは1作品につき生涯1個までLIGHT SEEDを送信できる。

翌月になっても同一ユーザーが同一作品へ再送信することはできない。

異なるユーザーから同じ作品が受け取るLIGHT SEED数には上限を設けない。

送信後の取消・種類変更は原則不可とする。

### LIGHT SEEDと作品Rankの完全分離

LIGHT SEEDの受取数は、作品Rankへ直接影響しない。

SEEDを大量に受け取ったことだけでRankが上がる仕組みにはしない。

これにより「SEEDを受ける → Rankが上がる → 発掘成功になる」という自己循環を防止する。

### LIGHT SEEDによる認知導線

作品カードには、その作品が受け取った累計LIGHT SEED数を表示する。

読者ホームには「最近LIGHT SEEDが送られた作品」枠を設ける。

その下に発掘用ランダム枠を設け、Rank 1〜2グループとRank 3〜4グループからそれぞれ作品をランダム表示する。

Rank 5 STARおよびRank 6 NOVAは、このランダム発掘枠には掲載しない。

LIGHT SEED数順のランキングにはせず、SEED集中がそのまま追加SEED集中を生む自己強化構造を避ける。

### LIGHT SEED使用時Scout XP

LIGHT SEED使用時には送信ユーザーへ以下のScout XPを付与する。

GOLD：30 XP
SILVER：20 XP
BRONZE：10 XP

月間11個をすべて使用した場合、LIGHT SEED使用だけで最大260 XPとなる。

### 発掘判定期間

LIGHT SEED送信時点の作品Rankを保存し、送信後180日以内の最高到達Rankによって発掘実績を判定する。

180日経過後のRank上昇では、そのSEEDに対する新しい発掘EXPは発生しない。

### 発掘成功段階

送信時Rankから+2 Rank：発掘成功、基礎150 XP。

+3 Rank：大発掘、基礎300 XP。

+4 Rank：特大発掘、基礎600 XP。

+5 Rank：NOVA発掘、基礎1,000 XP。

Rank 5 STARからRank 6 NOVAへの+1上昇は通常の発掘成功件数には含めず、「NOVA予見」とする。NOVA予見の基礎EXPは80 XPとする。

Rank 6 NOVAへ送信したLIGHT SEEDは使用時EXPのみ発生し、それ以上の発掘EXPは発生しない。

### LIGHT SEED種類による発掘EXP倍率

発掘成功時の基礎EXPには、送信したLIGHT SEED種類による倍率を適用する。

GOLD：×2.0
SILVER：×1.5
BRONZE：×1.0

例えば+2 Rank発掘成功は、BRONZE 150 XP、SILVER 225 XP、GOLD 300 XPとなる。

Rank 1からRank 6まで成長するNOVA発掘は、BRONZE 1,000 XP、SILVER 1,500 XP、GOLD 2,000 XPとなる。

NOVA予見はBRONZE 80 XP、SILVER 120 XP、GOLD 160 XPとなる。

### 発掘EXPの累計・二重取得防止

1ユーザー × 1作品につき1本の発掘記録として管理する。

同一SEEDについて発掘段階が上がった場合は、上位段階の累計EXPとの差額のみ追加付与する。

作品が一度Rank降格した後に再び同じRankへ戻っても、同一LIGHT SEEDから一度取得済みの発掘EXPを二重取得することはできない。

180日以内に到達した最高発掘段階まで記録をアップグレードする。

### ☆評価Scout XP

作品へ☆評価を行った場合、3 XPを付与する。

EXP対象は1日5作品までとし、☆評価による1日最大EXPは15 XPとする。

同一作品では生涯1回のみEXP対象とする。

評価変更、評価削除後の再評価では追加EXPを付与しない。

☆1でも☆5でも取得EXPは同じ3 XPとし、高評価ほどEXPが増える設計にはしない。

6作品目以降も☆評価自体は通常どおり利用可能とする。

### コメントScout XP

有効なコメント1件につき5 XPを付与する。

EXP対象は1日3作品までとし、コメントによる1日最大EXPは15 XPとする。

同一作品へ同日に複数コメントしてもEXP対象は最初の1回のみとする。

4作品目以降もコメント自体は通常どおり利用可能とする。

コメント文字数によってEXPを増減させない。

コピー・酷似コメント、短時間の異常大量投稿、BOT投稿、意味のない文字列その他EXP取得を主目的とした不自然な行動はEXP対象外または取消対象とする。

異常行動は、原則としてEXP停止・取消 → 警告 → 機能制限 → 悪質・反復時はアカウント停止の順で対応する。重大かつ明白なBOT・不正行為は即時措置を可能とする。

### 有効読書Scout XP

有効読書が作品単位で初めて成立した場合、1作品につき2 Scout XPを付与する。

有効読書Scout XPの対象は1日5作品までとし、1日最大10 XPとする。

同一ユーザーが同一作品から有効読書Scout XPを獲得できるのは原則として生涯1回とする。同一作品内で複数エピソードの有効読書が成立しても、有効読書Scout XPを重複付与しない。

有効読書そのものは本章の既存判定条件を維持し、単なるページ表示、放置、自作品閲覧、機械的反復をXP対象へ変換しない。

### Scout XPを付与しない行動

ログインだけではScout XPを付与しない。

お気に入り、フォロー、通常PV発生だけではScout XPを付与しない。

単に作品・エピソードを開いただけで有効読書判定を満たさない閲覧にはScout XPを付与しない。

LIGHT CHECK回答についても、本章または別の正式仕様で明示しない限りScout XP獲得条件へ自動追加しない。

### 有効読書

単に作品ページを開くだけでは有効読書としない。

通常エピソードでは、以下の複数シグナルを用いる。

- 本文40%以上まで到達
- ページが前面表示された状態で60秒以上の有効滞在
- 本文に対する一定量のスクロール・操作

有効読書の成立には、サーバー側時刻から積み上げた「ページが前面表示された状態での有効滞在」を必須シグナルとする。そのうえで、本文到達または本文に対する一定量のスクロール・操作の少なくとも一方を追加で満たすことを基本とする。クライアントから送信された進捗率と操作回数だけでは、有効読書を成立させない。

非常に短いエピソードは文字数に応じて到達率および必要な前面滞在を補正し、不自然な60秒待機を要求しない。ただし短編補正時も、クライアント申告だけで成立しないサーバー側時刻由来の前面滞在証拠を必須とする。

タブをバックグラウンドで開いたまま放置する時間は有効滞在として扱わない。

自作品は有効読書対象外とする。

作品紹介ページを開いただけでは対象外とする。

同一エピソードを機械的に繰り返し開いても、活動維持等では重複して有効読書としない。

具体的な内部判定式やBOT検知閾値は攻略防止のため完全公開せず、βデータから調整可能とする。

### Scout Level / Scout Rank / Scout Point / 称号

SCOUT RECORDはβ版から本実装する。

β版のScout Level上限はLv.30とする。Lv.30到達後はScout XPをそれ以上蓄積せず、以後に獲得条件を満たしたXPは消滅し、正式リリースへ持ち越さない。

正式リリース時、β版でLv.30へ到達したユーザーは最大Lv.30から開始し、Lv.30 / 次Level向けXP 0の状態からLv.31以降の成長を開始する。

## 39. 作品サムネイル・公式レイヤー合成方針

NOVELIGHTの作品サムネイルは、作者が任意の画像・写真・イラスト等を自由アップロードする方式を採用しない。

この禁止は作品一覧・検索・作品詳細等で使用する「作品サムネイル」に対する方針であり、第46章で定めるエピソード本文内の挿絵を禁止するものではない。本文挿絵は作品コンテンツの一部として、別の権利・ゾーニング・Storage・安全ルールに従って扱う。

これはβ版だけの制限ではなく、今後も原則として維持する。

権利侵害、成人向け・グロテスク等の不適切画像、作品と無関係な画像、著しい画質差等によって作品一覧全体の品質・安全性・NOVELIGHTのブランド統一感が損なわれることを防ぐため、作品サムネイルにはNOVELIGHT運営が用意・承認した公式素材のみを使用する。

従来検討していた「完成済みの本サムネイルから1枚を選択する方式」ではなく、β版から公式素材を組み合わせて1つの作品サムネイルを構成するレイヤー合成方式を基本とする。

サムネイルの基準キャンバスは、

1086 × 1448 px
縦横比 3:4

で統一する。

作者が選択する素材カテゴリは、下から上へ以下の5項目とする。

1. 背景
2. 基準本
3. 背景模様
4. 中央シンボル
5. 枠

背景と基準本は基本構成として必須とする。

背景模様、中央シンボル、枠については「なし」を選択可能とし、すべての作品へ装飾を強制しない。

表紙カラー・質感を基準本の上へ別レイヤーとして貼る方式は採用しない。色、材質、装丁の違いを増やす場合は、紙状の表紙レイヤーを重ねるのではなく、完成した本そのものを `base_book` の公式素材として追加する。

光・粒子・霧等のeffectレイヤーは作者向け機能として採用しない。

作者向け素材選択UIは、背景、基準本、背景模様、中央シンボル、枠の5カテゴリをそれぞれ折りたためるアコーディオンバーとして表示する。原則として同時に開くカテゴリは1つとし、閉じたバーにも現在の選択素材名を表示する。素材数が増えた場合も画面全体が無制限に縦長化しないよう、開いたカテゴリ内の素材一覧はスクロール可能な領域に収める。

作者向け素材選択UIには「おまかせで選ぶ」ボタンを設ける。押下時は現在のテンプレート内で、背景・基準本・背景模様・中央シンボル・枠の5カテゴリだけをランダムに再選択する。背景と基準本は必ず公式素材を1件選択し、背景模様・中央シンボル・枠は「なし」もランダム候補に含める。内部互換用の `cover`、廃止済みの `effect`、テンプレートGeometryその他の非作者向け状態は変更しない。可能な候補が複数あるカテゴリでは、押下直前と同じ候補を除外して再選択し、「押したのに何も変わらない」体験をできるだけ避ける。

作者が各素材をドラッグして自由配置、回転、拡大縮小する方式にはしない。

NOVELIGHT側で本の位置、角度、遠近、表紙面、安全領域をテンプレートとして固定し、作者は公式素材を選択するだけで正常なサムネイルが完成する仕組みとする。

各素材は同一テンプレート内で共通座標を使用し、単純に同じ原点へ重ねても位置ずれ・はみ出しが起きない規格とする。

β初期は原則として1種類の基準本ジオメトリを正式テンプレートとして使用する。

将来、異なる形・角度の基準本を追加する場合はtemplate key等によって互換グループを分離し、互換性のない模様、シンボル、枠等を重ねない。

背景模様、中央シンボル、枠等、表紙面内に収めるべき素材は、テンプレートごとの表紙Geometryによって表紙外へはみ出さないようにする。

この表紙Geometryはレンダリング用の内部情報であり、作者が選択する追加レイヤーにはしない。

背景は基準本と独立して変更可能とする。

ただし、基準本の固定位置、接地面、遠近等と大きく矛盾しない公式背景のみを登録し、背景を変更しても本が不自然に浮く・沈む・位置がずれる状態を避ける。

作品タイトル、作者名、ジャンルその他の作品カード上の文字情報は、サムネイル画像へ焼き込む必須レイヤーにはせず、原則として既存の作品カードUI側で表示する。

作者が選択できるのはADMINで有効化されたNOVELIGHT公式素材のみとする。

公式素材はADMINから追加・管理できる構造とし、新しい素材を追加するたびにコード変更・デプロイを必要としない運用を目指す。

ADMINでは少なくとも、

素材ファイル
表示名
レイヤー種別
対応テンプレート
表示順
公開状態

を管理できるようにする。

素材は公開中、選択終了、緊急無効等を区別できる構造を持たせ、すでに作品で使用中の素材を安易に物理削除しない。

作者・一般ユーザーから公式素材Storage・素材管理テーブルへ直接書き込める権限は付与しない。

作者は公式素材IDを選択して自分の作品へ保存するだけとし、任意ファイルや任意URLをサムネイルへ差し込めないようにする。

作品ごとに選択した5カテゴリの素材IDを構成情報として保持する。既存DBに残る旧 `cover` / `effect` 列は移行互換のため内部的に保持してよいが、作者向けの選択肢・描画正本にはしない。

将来的な再編集・素材差し替えに対応できるよう、完成画像だけを唯一の正本として保存する方式にはしない。

一方、作品一覧・おすすめ・検索・ランキング等で複数の素材画像を毎回個別ロードすることによる性能低下を避けるため、選択素材IDを正本として保持しながら、表示用には合成済みサムネイルを生成・キャッシュできる設計を基本とする。

素材追加の目的は自由度を無制限に高めることではない。

NOVELIGHT全体の品質・統一感を守りながら、作者が自分の作品に合う見た目を選び、同じ完成済みサムネイルばかりが並ぶ状態を避けることを目的とする。

β版では素材数を無理に増やすより、レイヤー位置、合成品質、選択UX、表示速度、スマートフォン表示、ADMIN運用が安定することを優先し、素材種類は運用しながら追加する。

## 40. Geometry Thumbnail Engine正式仕様

本章は、第39章「作品サムネイル・公式レイヤー合成方針」を実装する共通ジオメトリ基盤として、Geometry Thumbnail Engineの正式仕様を定める。本章の具体仕様と第39章の内部表紙マスク等に関する記述が矛盾する場合は、本章を優先する。

### 基本方針

Geometry Thumbnail Engineは、公式テンプレート上の本の各面を数値化されたジオメトリとして扱い、作者が選択した公式レイヤーを同じレンダリング規則で決定論的に合成する共通エンジンとする。

テンプレート固有の座標補正や画像ごとの例外処理をレンダラーへ埋め込まず、ジオメトリと表示許可範囲をテンプレートデータ側に保持する。

### Source of Truth

各公式テンプレートの表紙レンダリングは `base_book + cover_quad` をSource of Truthとする。

`base_book`はテンプレートの基準本画像、`cover_quad`はその基準本画像上で表紙面を表す4頂点の座標データとする。

表紙の形状、遠近、クリッピング、Perspective Transformは `cover_quad` から導出し、別のPNGマスク、手作業で調整した座標、CSS上の個別補正等を正本として並存させない。

第39章で定義した「内部表紙マスク」は、`cover_quad` から必要に応じて導出されるクリッピング・検証・デバッグ上の補助表現を指す。PNGマスクはデバッグ用途のみとし、レンダリングの正本として使用しない。

PNGマスクと `cover_quad` に差異がある場合は `cover_quad` を正とし、PNG側を再生成する。PNGマスクを手動修正してGeometryを合わせる運用は禁止する。

### 表紙レイヤーのPerspective Transform

`pattern`、`symbol`、`frame` は、テンプレートの正規化された表紙平面を入力座標系として扱い、`cover_quad` へPerspective Transformして描画する。

これらのレイヤーは表紙面ジオメトリに追従し、基準本の角度・遠近・台形変形が変わっても、エンジン共通の変換処理によって正しい表紙位置へ投影する。

`pattern`、`symbol`、`frame` は原則として `cover_quad` の表紙領域内へクリップし、表紙外へ描画しない。

`cover_texture` と `effect` は作者向け描画レイヤーとして採用しない。既存DB・migrationにこれらの互換列や設定が残る場合も、作者UI・新規素材登録・通常レンダリングでは使用しない。色や材質の違いは `base_book` 素材として表現する。

背景と `base_book` は表紙Perspective Transformの対象外とし、テンプレートの基準キャンバス上へ規定どおり描画する。

### Geometry Validation

`cover_quad` を保存・公開・レンダリング対象へ昇格させる前にGeometry Validationを必須とする。

最低限、以下を検証する。

- 頂点数が正確に4点であること
- 各座標が有限数であり、想定キャンバスと明らかに矛盾する値ではないこと
- 4頂点が重複せず、面積が0または実用不能な極小値になっていないこと
- 辺が自己交差せず、頂点順序が一貫していること
- Perspective Transformを一意かつ安定して計算できること
- テンプレートの基準キャンバス、`base_book`、`cover_quad` の組み合わせが同一テンプレートとして成立していること

Validationに失敗したGeometryは公開テンプレートとして有効化しない。無効な `cover_quad` をPNGマスクや旧座標へ黙ってフォールバックして描画する実装は行わない。

Validationルールは将来の複雑な本形状へ対応できるよう拡張可能とするが、同じ入力に対して同じ判定となる決定論的な処理を維持する。

### ADMIN Geometry Editor

ADMINには公式テンプレートごとのGeometry Editorを設ける。

`cover_quad` の4頂点をプレビュー上でドラッグして編集できるようにし、各頂点のx/y座標を数値入力でも直接編集できるようにする。

ドラッグ編集と数値入力は常に同一の `cover_quad` データを更新し、片方だけに存在する別座標を持たない。

編集画面では、`base_book` 上へ `cover_quad`、変換後の `pattern`、`symbol`、`frame` をリアルタイムプレビューし、実際のGeometry Thumbnail Engineと同じ変換ロジックで結果を確認できるようにする。

保存前にGeometry Validation結果を表示し、Validationに失敗している状態では公開中テンプレートの正本Geometryとして確定できないようにする。

ADMINは運営用のGeometry編集手段であり、作者へ4頂点編集を開放しない。作者は第39章どおり、承認済み公式テンプレートと公式素材を選択するだけとする。

### 将来拡張

Geometry Thumbnail Engineは表紙面だけに固定された使い捨て実装にしない。

将来的に必要となった場合、同じテンプレートに以下の面Geometryを追加できる構造とする。

- `spine_quad`
- `page_quad`
- `edge_quad`

これらは必要なテンプレートにのみ追加するオプションGeometryとし、未定義のテンプレートへ無理に持たせない。

将来の新しい面も、座標データ、Validation、Transform、クリッピング等を共通Geometryモデルへ拡張することを原則とし、特定テンプレート専用の描画分岐を増殖させない。

### 全公式テンプレート共通基盤

Geometry Thumbnail EngineをNOVELIGHTの全公式サムネイルテンプレート共通基盤とする。

公式テンプレートごとに別レンダラーや個別座標補正コードを作らず、同一エンジンへテンプレートデータを渡して描画する。

新しい公式テンプレートを追加する場合は、原則としてエンジンを変更せず、`base_book`、`cover_quad`、背景・背景模様・中央シンボル・枠の必要な公式素材、将来のオプションGeometry等のテンプレートデータを追加するだけで対応できる構造とする。

エンジン変更を必要とするのは、既存データモデルでは表現できない新しいGeometry能力をNOVELIGHT全体へ追加する場合に限る。テンプレート固有の見た目を成立させるためだけの例外分岐は追加しない。

この原則により、テンプレート追加数が増えても、描画品質、Validation、ADMINプレビュー、キャッシュ生成等が同じ基盤を利用し、テンプレートごとの実装差による不具合を抑える。

LIGHT SEED送信時Rankの保存、180日間の発掘成功判定、SCOUT関連の再計算・分析、作品成長の内部判定等には通常どおり利用する。

一方、β期間中は作品成長Rankを読者・作者へ表示しない。作品カード、作品詳細、ランキングその他の一般ユーザー向け画面に、Rank 1〜6、EMBER、SPARK、GLOW、BEACON、STAR、NOVA等の現在Rankを表示しない。

β初期は作品数・評価件数・読者数が少なく、相対分布を含むRankが母集団の増減によって変動しやすいため、Rankを作品の優劣・格付けとして受け取られること、低Rank作品がさらに選ばれにくくなる自己強化、不必要な作者間格差・不満を避けることを優先する。

ADMINでは運営・検証に必要な範囲で作品Rankを確認可能としてよい。

正式リリース後も作品Rankを自動的に一般公開することは確定事項としない。β実データによる安定性、ユーザー理解、作品発見への影響を確認したうえで、公開するか、内部指標として維持するかを別途決定する。

将来作品Rankを一般公開すると決定した場合に限り、第38章の「数字＋名称」のUI表記原則を適用する。

### β版ホームの発掘棚

作品Rankそのものは非公開とする一方、内部Rankは作品発見アルゴリズムとして利用する。

β版ホームでは、カタログと対象作品数が成立する範囲で、以下の順を基本とする。

1. あなたへのおすすめ・発見棚
2. 新着作品
3. LIGHT SEEDで発掘中
4. まだ知られていない物語
5. いま光が集まりはじめた物語

「まだ知られていない物語」は内部Rank 1〜2グループを候補母集団とする。

「いま光が集まりはじめた物語」は内部Rank 3〜4グループを候補母集団とする。

読者向けUIには「Rank 1〜2」「Rank 3〜4」等の内部Rank区分を表示せず、作品発見テーマとして提示する。

Rank 5 STARおよびRank 6 NOVAは、第38章どおりこのランダム発掘枠の対象外とする。

LIGHT SEEDで発掘中は、LIGHT SEEDを受け取った公開作品が存在するときに表示する。対象作品が存在しない段階で空棚を常設しない。

内部Rank別発掘棚も、対象作品が少なすぎる場合に同一作品の反復でサービス規模を小さく見せないよう、十分な候補が存在するときに表示・ローテーションする。

### β期間中のSCOUT RECORD表示

作品成長Rankは、作品カード・検索・ランキング等の一般的な作品評価表示としてはβ期間中非公開とする。一方、読者本人のSCOUT RECORDにおける自分の発掘履歴と、権限のあるADMIN分析では、発掘の成長経路を理解できるよう正式Rank名称を表示してよい。

β版では、Scout Level、Scout Rank、Scout XP進捗、Scout Point、読者称号、作者称号、限定称号、LIGHT SEED履歴、発掘成功・発掘段階等を第49章の公開範囲に従って表示する。

作品Rankの正式名称は EMBER / SPARK / GLOW / BEACON / STAR / NOVA とする。作品カード・検索・ランキング等へ常時表示しない方針は維持するが、SCOUT RECORDの本人向け発掘履歴では「送信時 EMBER → 最高 GLOW」のように表示してよい。作品RankとScout Rankは別概念であり、混同しない。

本人にはSCOUT RECORDの詳細を表示できるが、他ユーザーへScout Point残高・Point履歴、詳細XP、次LevelまでのXP、詳細行動ログ、不正確認状態等を公開しない。

Lv.30到達時は通常XPバーから「β LEVEL MAX」表示へ切り替え、Lv.30到達後のXPは蓄積されず消滅すること、Scout Point・称号・発掘実績は継続取得できること、正式リリース後にLv.30以降を解放することを明確に告知する。

β版からPoint残高・履歴を表示するが、正式リリース前の交換レート・金銭換算価値を断定表示しない。

SCOUT RECORD本実装以前の既存行動をどこまで遡及反映するかは未確定とし、実装時に勝手に再計算・付与しない。

### 読者の閲覧と登録導線

公開作品および公開エピソードは、読者登録・ログインを必須とせず閲覧可能とする。

基本的な読書を会員登録で遮断して登録者数だけを増やす設計にはしない。まず作品を読める状態を提供し、その後のユーザー固有行動で自然に登録を促す。

お気に入り、エピソードハート、LIGHT SEED、SCOUT関連の記録その他アカウントに紐づく行動は、認証が必要な機能として扱う。

未登録読者がこれらの行動を行おうとした場合は、読書中の文脈を失わせない形でログイン・新規登録へ誘導する。

基本導線は、

作品を発見する
→ 登録なしで読む
→ 気に入る・発掘したい
→ お気に入り／エピソードハート／LIGHT SEED等を行う
→ 必要な時点で登録する

とする。

### β公開前後の読者・作者集客優先順位

2026年9月30日のβ版公開までは、読み専ユーザーの先行登録を主要KPI・主要キャンペーンにせず、先行作者の獲得と作品在庫の形成を優先する。

読者向けの独立した先行登録キャンペーンをβ公開前の必須施策にはしない。

これは読者獲得を停止する方針ではない。作品数、ジャンル、更新作品、LIGHT SEED対象作品等が蓄積し、読者が訪問した際に十分な発見・読書体験を提供できる段階から読者集客を強化する。

β公開後は、実際の作品を入口として読者を獲得し、お気に入り、LIGHT SEED、将来のSCOUT RECORD等を登録理由へ接続する。

第8章の「作家獲得 ＞ 読者獲得」を維持しつつ、作品在庫と読者体験が成立した段階で「作家獲得 ≒ 読者獲得」へ移行する。

## 42. 他社サービス調査・有益機能採用原則

NOVELIGHTは、「他社にすでに存在する機能だから独自性がない」という理由だけで、有用な機能の採用を避けない。

小説投稿サービス、創作支援サービス、読書サービスその他の周辺プロダクトに、作者・読者・運営の実際の課題を解決している有益な機能・UXパターンが存在する場合、NOVELIGHTの基本思想と矛盾しない範囲で積極的に調査し、採用候補とする。

内部で俗に「他社の良い機能をパクる」と表現する場合も、その意味は「他社が解決しているユーザー課題と機能パターンを学び、NOVELIGHT向けに再設計して採用する」こととする。

他社のソースコード、文章、デザイン、画像・素材、固有名称、商標、非公開アルゴリズム、非公開データ等を複製することは、この方針に含まれない。

### 採用判断の基本原則

他社機能を確認した場合、まずNOVELIGHTの現行MASTERとcurrent mainを確認し、すでに同じ問題を解決する機能が存在しないかを調べる。

機能名・画面構成が異なっていても、目的が同じ既存機能がある場合は重複実装を避け、必要なら既存機能の改善として扱う。

未実装であり、ユーザー価値が確認できる場合は、以下を満たすかを評価する。

- 評価される前の機会格差を減らすという原則を壊さないか
- 課金で評価・ランキング順位・作品価値そのものを買わせないか
- 作者が書き続ける、または読者が読み続ける理由を増やすか
- 人気作者・大規模コミュニティ・既存フォロワー等の力だけで露出や評価が自己増殖しないか
- 馴れ合い評価、談合、BOT、スパム、嫌がらせ、権力化等の悪用を抑制できるか
- 読者課金なしという現行の事業方針と矛盾しないか
- 作品サムネイルその他NOVELIGHT固有の安全・ブランド方針と矛盾しないか
- 著作権、商標、プライバシー、利用規約、外部サービス規約その他の法務・権利上の問題を生まないか
- 運用・セキュリティ・保守コストに対して十分な実益があるか
- 今実装する必要があるか

条件を満たす場合、他社由来の一般的な機能であることを理由に却下しない。

### 複数サービスで定着している基礎機能

複数の主要サービスで継続的に採用され、同じユーザー課題を解決している機能は、「業界の基礎便利機能」である可能性が高い。

この種の機能は、NOVELIGHT独自機能より価値が低いとは考えない。作者・読者が他サービスでは当然に利用できる基礎機能がNOVELIGHTに存在しないことによって、乗り換え・継続利用の障壁が生まれる場合は、強い採用候補として扱う。

ただし、「他社にある」という事実だけでA優先へ昇格させない。第24章のA／B／C分類と「今やる必要があるか」を維持する。

### NOVELIGHT向け再設計

採用する場合は、他社の画面や名称をそのまま再現するのではなく、NOVELIGHTの既存データモデル、UI、世界観、安全方針、露出設計、LIGHT SEED、SCOUT、LIGHT ANALYTICS等との関係を整理し、NOVELIGHTの機能として再設計する。

他社より単純・安全・分かりやすい形で同じ問題を解決できる場合は、他社の実装粒度に合わせる必要はない。

逆に、他社の機能を導入することでNOVELIGHT独自の公平性や発見体験が弱くなる場合は、そのまま採用せず、機能を分離・制限・再構成する。

### 優先順位の考え方

競合監査で発見した未実装機能は、原則として以下の順で優先度を評価する。

A候補：安全性、セキュリティ、データ保護、作者の作品持ち出し・復旧、アクセシビリティ、重大な読書・投稿UX等。

B候補：作者生産性、長編管理、読者継続、作品整理、作者フォロー、通知、検索・発見等、継続率を大きく改善する機能。

B〜C候補：高度なコミュニティ、SNS的機能、AI支援、娯楽的演出、共同創作、追加のゲーミフィケーション等。

優先順位は固定ではなく、β実データ、ユーザー要望、競合環境、実装コスト、不正リスクから更新する。

### 原則としてそのまま採用しないパターン

以下は他社に存在していても、そのままNOVELIGHTへ持ち込まない。

- 読者課金を前提とするギフト・投げ銭・有料閲覧
- 課金額や応援アイテムを作品評価・作品Rankへ直接加点する仕組み
- 既存フォロワー数・知名度・人気だけで露出が自己増殖する仕組み
- 馴れ合い評価・評価交換・相互支援を促進する構造
- ユーザーによる任意サムネイル画像アップロード等、第39・40章の安全方針と矛盾する仕組み
- 作品投稿・読書よりタイムラインやDMが主役になる過度なSNS化
- 他社固有の名称、文章、UI、コード、素材その他の知的財産の複製

拒否対象であっても、その機能が解決している問題自体は分析し、NOVELIGHTの原則を守る別手段で解決できないかを検討する。

### 競合機能監査台帳

競合・周辺サービスの調査結果は、MASTERへサービスごとの細かな機能一覧を増やし続けるのではなく、別の監査文書へスナップショットとして保存する。

監査では少なくとも、

- 調査対象サービス
- 確認した機能
- 解決しているユーザー課題
- NOVELIGHTでの既実装／部分実装／未実装
- NOVELIGHT原則との適合性
- 不正・安全・法務・プライバシー上の注意点
- A／B／C候補
- 採用／見送り／再評価の理由
- 実装後のPR・仕様等の証拠

を可能な範囲で記録する。

2026年9月16日時点の初回横断監査は `docs/COMPETITOR-FEATURE-AUDIT-2026-09-16.md` を参照する。

### 継続的な再監査

競合調査は一度で終了しない。

β公開前後、正式リリース設計時、料金・発見・コミュニティ等の主要方針変更時、主要競合が大規模な新機能を公開した場合等に再監査する。

新しい競合サービスが成長した場合も調査対象へ加える。終了・縮小したサービスの機能は歴史的参考として扱い、現在の業界標準を判断する唯一の根拠にはしない。

NOVELIGHTの目的は「他社と同じ機能数にすること」ではない。

他社で有効性が確認されている基礎的な便利さは合理的に取り込みながら、NOVELIGHT独自の公平な発見機会、LIGHT SEED、SCOUT、LIGHT ANALYTICS等へ開発資源を集中し、作者・読者にとって総合的に使いやすく、長く使い続けられるサービスを作る。

## 43. 競合監査から採用した作者投稿補助の基礎機能

第42章の方針に基づき、複数の小説投稿・創作支援サービスで定着している作者向け基礎便利機能のうち、NOVELIGHTの公平性・安全性・読者課金なし方針と矛盾しないものは、既存機構を壊さない形で段階導入する。

これらの作者投稿補助機能は、作品Rank、LIGHT SEED、SCOUT、PV、発見棚、検索順位、露出保証その他の評価・発見ロジックへ直接加点しない。作者が安全に書き、管理し、公開し続けるための利便性として扱う。

### 安全な小説向け本文記法

本文保存の正本は引き続きプレーンテキストとする。

作者は必要性の高い小説向け表現として、少なくとも以下の限定記法を利用できる。

- ルビ：`｜漢字《かんじ》`
- 傍点：`《《強調》》`

保存時に任意HTMLへ変換せず、読者表示・作者プレビュー等のpresentation時だけ安全なallowlist DOMへ変換する。

作者本文に含まれるHTMLらしい文字列、script、event handlerその他の任意HTMLをブラウザHTMLとして解釈しない。

壊れた記法、上限を超える記法、複数行へまたがる不正な記法等は、作者本文を破壊せず原則として文字列のまま表示する。

読者表示と作者プレビューは同一の安全なレンダリング規則を使用し、本文記法の導入によってPV、有効読書、Rank、LIGHT SEED、SCOUTその他の評価・計測条件を変更しない。

### 複数話の予約公開管理

既存の単発予約公開を廃止・複製せず、`episodes.scheduled_publish_at` と既存のdatabase-side due publication workerを予約公開のSource of Truthとして維持する。

作者は自作品の非公開下書きについて、予約一覧を確認し、複数話の公開日時をまとめて設定・変更・解除できる。

作者UIでは、複数の下書きを選択し、開始日時と公開間隔から時間割をまとめて入力できる。個別の日時修正、一括解除も可能とする。

複数話の変更はowner-boundのdatabase RPCで原子的に保存する。一部だけ成功して残りが失敗する状態を作らず、入力・所有権・公開条件・順序条件のいずれかが不正な場合は当該batch全体を失敗させる。

1回のbatchで扱う変更件数には上限を置く。βでは最大50話を基本上限とする。

未公開作品を予約公開する場合、第1話が最初の公開でなければならない。第2話以降の予約日時は第1話より後でなければならず、同時刻または先行時刻によって第2話以降が先に公開される時間割を受け付けない。

作品がすでに公開済みの場合は、複数の後続話を同一時刻に予約すること自体は許容できる。実際の公開処理は既存のdue publication workerが担当し、新しいcron・第二の予約テーブル・第二の公開executorを追加しない。

予約中のエピソードは実際の公開時刻まで`draft`のままとし、既存RLSにより一般読者へ公開しない。

手動公開、既存単発予約、章・並び順管理、改稿履歴、作者バックアップその他の既存作者機能と共存させる。B #13のrollbackはbatch管理RPCだけを除去し、既存の`scheduled_publish_at`、既存予約データ、既存cron、既存due publication workerを削除しない。

コードが先に配信されProduction migrationが未反映の期間は、作者UIをfail-safeに扱い、「データベース反映待ち」として破損操作を許可しない。

Production migrationの適用は、PR mergeとは別の明示承認境界とする。


### 登場人物の自動出現管理と読者向け一覧

長編作品で「この人物は誰だったか」「直近でいつ出たか」を読者が安全に確認できるよう、作品ごとの登場人物レジストリを持つ。

登場人物の正本は作品ごとに1つとし、作者は名前、別名・呼び名、自動検出ON/OFF、読者表示ON/OFFを管理できる。

一度登録した人物は、既存エピソードを再判定し、その後もエピソード本文の保存・更新時に名前または登録済み別名を本文から自動検出する。本文保存の第二経路を作らず、既存のエピソード保存をSource of Truthとしてdatabase-sideの派生状態を更新する。

各エピソードでは作者が以下を手動指定できる。

- 自動判定に戻す
- この話に含める
- この話から除外する

手動の含める／除外する指定は自動判定より優先する。自動判定をOFFにした人物も手動指定は利用できる。

読者向け一覧は、現在読んでいる公開エピソードまでに実際に登場済みの人物だけを返す。現在話より後の公開話、下書き、未来の登場予定、作者だけが知る別名その他の未到達情報を読者へ漏らさない。

読者一覧の基本順序は、

1. 現在話に登場している人物
2. 直近の登場話が新しい人物
3. その他の既出人物

とする。各人物には、現在話に登場しているか、または読者が到達済み範囲での直近登場話を表示できる。

作者側の自動検出ON/OFFと読者表示ON/OFFは分離する。自動検出は使うが読者一覧には出さない人物、または自動検出せず作者が各話で手動指定する人物を許容する。

生の登場人物レジストリ、別名、エピソード別の内部判定状態は一般クライアントへ直接公開しない。RLSと権限をfail-closedにし、作者管理はowner-bound RPC、読者表示は未来情報を除去した専用RPCだけを利用する。

ネタバレ境界は登場人物機能だけに限定しない。作品目次、更新通知、本棚、読書再開、前後話ナビその他の自動表示・prefetch・API responseでは、読者が有効読書として到達済みの話より後のエピソードタイトル、章タイトルその他の内容示唆情報を先回りして返さない。未到達話への移動に必要なエピソードID・話数は返してよいが、表示は「第N話」等の中立表現とする。

公開済みエピソードは、読者がURLや「次の話を読む」操作で意図的に開いた時点では通常どおり本文とタイトルを表示する。このネタバレ境界は、公開済み本文そのものを秘密情報としてアクセス禁止にするものではなく、通常導線が未来情報を自動的に先読み・露出しないためのUX境界である。

この機能は作品Rank、LIGHT SEED、SCOUT、PV、お気に入り、検索順位、発見棚、露出その他の評価・発見シグナルへ加点しない。読書理解と作者管理を補助する機能として扱う。

β実装ではAIによる人物抽出・人物同定を必須にしない。まずは作者が登録した名前・別名と手動overrideによる再現性の高い判定を正本とし、AI補助は将来必要性が確認された場合に別途検討する。

コードが先に配信されProduction migrationが未反映の期間は、読者側は当該一覧を非表示、作者側は「データベース反映待ち」としてfail-safeに扱う。

### 下書き作品の限定公開／共有リンク

競合監査 #16 の限定公開／共有リンクは、通常公開とは別の「共有・確認用途」として実装する。

β版では新しい作品公開statusや一般向けvisibility区分を増やさず、限定共有中も作品のSource of Truthは `novels.status = 'draft'` のままとする。これにより既存RLS、検索、作品Rank、LIGHT SEED、SCOUT、PV、お気に入り、発見棚、露出その他の通常公開ロジックへ限定共有作品を混入させない。

限定共有は作品ごとに有効な共有リンクを最大1本とし、作者本人だけが発行、再発行、停止できる。再発行した場合、それ以前の共有リンクは即時無効とする。

共有トークンは十分に推測困難なランダム値とし、databaseには生トークンを保存せずハッシュのみを保存する。生トークンは発行・再発行時に作者へ一度だけ返し、後からdatabaseから復元・再表示しない。作者がURLを失った場合は再発行する。

共有URLでは秘密値を通常のquery parameterへ置かず、ブラウザのURL fragmentへ保持する。共有読書ページはreferrerを送信しない設定とし、共有トークンを通常のHTTP request URLや外部参照先へ不要に露出させない。

共有相手は専用のtoken-bound reader RPCを通じて、共有作品の基本情報と現在保存されているエピソード本文を確認できる。通常の `novels` / `episodes` SELECT RLSを緩和せず、生の共有リンク管理テーブル、token hash、作者専用状態その他の内部情報を一般クライアントへ直接公開しない。

共有読書は通常公開ではないため、PVを増加させず、お気に入り、LIGHT SEED、SCOUT、作品Rank、検索、発見棚、露出、コメントその他の通常読者行動・評価・発見シグナルへ接続しない。共有ページにはこれらの通常公開用UIを載せない。

共有リンクを持つ相手には、当該作品に現在保存されている共有対象エピソード本文を読めることを作者UIで明示し、信頼できる相手だけへ共有するよう案内する。

作品が通常公開へ移行した場合、または作品所有者が変更された場合は、有効な限定共有リンクをdatabase-sideで自動失効させる。公開後は通常の作品ページを利用し、旧共有URLから下書き用reader RPCで読み続けられない状態とする。

一般読者向けの共有reader RPCは、意図的に公開する最小限の `SECURITY DEFINER` endpointとして扱う。厳格なtoken形式検証、token hash照合、`draft`状態の再確認、最小限の返却項目、書き込み・評価イベント非生成を必須とし、内部ID、PV、Rank、SCOUT、お気に入り、露出状態等を返さない。

コードが先に配信されProduction migrationが未反映の期間は、作者側を「データベース反映待ち」として発行操作を停止し、共有読書側も利用不可としてfail-safeに扱う。通常テーブル読み取り等へフォールバックして限定公開を再現しない。

B #16のrollbackは、有効な共有リンクが存在する場合は限定共有を突然解除・露出させるリスクを避けるため拒否する。有効リンクが存在しない場合のみ、限定共有固有のtable、RPC、triggerを除去し、既存の作品・エピソード・RLS・公開処理を維持する。

### 本人専用の読書履歴・個人読書統計

競合監査 #17 の読書履歴・個人読書統計は、読者が自分の読書を振り返り、NOVELIGHTで読み続ける理由を増やすための本人専用機能として採用する。

β版では、統計表示のためだけに第二の読書トラッカーや追加の閲覧イベントを新設しない。SCOUT/LIGHT SEEDの有効読書判定のため既に保存されている `valid_read_events` を、読書履歴のSource of Truthとして再利用する。

`valid_read_events` は同一読者・同一エピソードにつき初回の有効読書を1件だけ保持するため、β版の読書履歴は「その話で最初に有効読書が成立した記録」として扱う。同じ話の再読回数、再読した日数、総滞在時間等を記録したものとして表示・説明してはならない。

β版の本人向け基本統計は、少なくとも以下とする。

- 有効読書したエピソード数
- 有効読書した作品数
- 初回の有効読書が1件以上成立した読書日数
- 本棚で本人が「読了」に設定した作品数
- 有効読書した作品ベースのジャンル傾向
- 最近の初回有効読書履歴

読書日数は日本時間（Asia/Tokyo）の日付境界で集計する。

ジャンル傾向はエピソード数ではなく、少なくとも1件の有効読書がある作品を作品単位で集計する。長編で話数が多い作品だけがジャンル傾向を過度に支配しないようにする。

本棚の「読了」は読者本人が設定する整理状態であり、NOVELIGHTが本文全話の実読了を自動判定した数値として扱わない。UIでは「読了にした作品」等、意味を誤認しない表現を使用する。

履歴一覧で作品名・エピソード名・リンク等の現在情報を表示する場合は、その時点で作品とエピソードの両方が公開中であることを再確認する。下書き化・非公開化された現在非公開コンテンツを、過去に読んだという理由だけで本人向け履歴から再公開しない。

生の `valid_read_events`、有効読書判定シグナル、内部ルールその他のSCOUT用行動台帳を一般クライアントへ直接公開しない。本人向け履歴・統計は、`auth.uid()` に固定した最小限の集計RPCから必要な項目だけを返す。

読書履歴・ジャンル傾向・個人統計はβ版では公開プロフィール機能にしない。他ユーザー、作者、一般公開ページから閲覧できる共有設定を設けず、ログイン中の本人だけが確認できる状態を基本とする。将来公開設定を検討する場合は、プライバシーとユーザー同意を別途設計する。

既存の `reader_reading_progress` はクロスデバイスの読書再開位置、`reader_bookshelf_entries` は本人用の本棚整理をSource of Truthとして維持し、#17のためにこれらを第二の履歴台帳へ複製しない。

### 説明可能な自然文作品検索（β）

競合監査 #24 のセマンティック／対話型作品検索は、β版では「こういう話を読みたい」という自然文から公開作品を探せる、説明可能な自然文作品検索として採用する。

自然文からジャンル、重要語、あらかじめ定義した近義概念を決定論的に抽出し、既存の中立的な公開作品検索を候補取得に再利用する。関連度はタイトル・あらすじ・ジャンルとの一致だけから算出し、作品Rank、LIGHT SEED、SCOUT、PV、お気に入り、作者フォロワー数、契約プラン、追加露出その他の人気・課金・評価シグナルを関連度加点へ利用しない。

検索結果には、可能な範囲で「ジャンルが一致」「この語がタイトル／あらすじに一致」「この概念に近い語が一致」等の理由を表示し、なぜ候補になったかを読者が確認できるようにする。自然文検索を作品品質のAI評価やおすすめ保証として表現しない。

β版では外部LLM・外部Embedding APIへ作品本文やユーザーの検索対象データを送信せず、新しいSecretや従量課金APIを必須にしない。将来、Embeddingや生成AIを使った本格的な意味検索・対話的絞り込みへ拡張する場合は、検索精度だけでなく、コスト、プライバシー、成人向けゾーニング、プロンプト誘導、不正な露出操作、説明可能性を別途検証してから導入する。

自然文検索の候補取得は既存の公開検索RPCを利用し、候補取得自体をインプレッションとして数えない。実際に読者画面へ表示した検索結果だけを、既存の中立検索インプレッション契約に従って記録する。

既存のBlock／Mute、成熟テーマその他の読者安全フィルタは自然文検索にも適用し、検索機能の追加を理由にそれらを迂回しない。

β版のユーザー向け名称は「自然文で探す β」とし、会話履歴を保持するチャット型検索までは必須範囲に含めない。まず自然文1入力からの発見価値、検索結果の納得感、利用率を確認し、対話的な追加絞り込みはβデータから再評価する。

### 競合監査採用機能の共通原則

これらは他社の文章、UI、コード、名称、素材、非公開アルゴリズム等を複製したものではなく、第42章に従い、他社が解決している一般的なユーザー課題・機能パターンをNOVELIGHT向けに再設計した機能として扱う。

作者・読者の利便性を目的とする機能は、別途MASTERで明示された場合を除き、作品Rank、LIGHT SEED、Scout XP、PV、検索順位、発見棚、追加露出その他の評価・発見シグナルへ直接加点しない。

private dataを扱う機能は、raw tableを一般クライアントへ安易に公開せず、RLS、owner-bound access、必要最小限のRPC等によって権限境界を守る。Block、非公開作品、下書き、限定共有、未到達ネタバレその他の既存安全境界を、新しい便利機能の追加を理由に迂回しない。

### 作者向け作品エクスポート／バックアップ（#1）

作品の権利は作者にあるという第29章の原則に基づき、作者は自分の作品を外部へ持ち出せる。β版の基本出力は作者本人専用のTXTバックアップとし、作品メタデータ、所有する全エピソードの本文、公開状態、予約公開日時等を含める。

他ユーザー作品の出力は許可しない。認可は表示側だけでなくdatabase-sideで本人所有を確認する。短時間の大量実行には上限を設け、バックアップ操作はprivate auditとして記録可能とする。

バックアップにはPV、お気に入り、作品Rank、LIGHT SEED、SCOUTその他の他者評価・内部評価データを作品本文の所有データとして混入させない。将来、本文挿絵等の作品構成要素を追加した場合は、バックアップによって作品の再利用に必要な参照情報を黙って失わないよう拡張する。

### Block／Mute（#2）

Blockは対象ユーザーとの直接相互作用を安全に抑制する機能とする。コメント、フォロー、アンケート、共同執筆その他、直接交流に当たる新機能を追加する場合もBlock境界との整合を確認する。

Muteは本人の表示体験を調整するpresentation機能とし、作品評価、作品Rank、LIGHT SEED、SCOUT、露出その他の評価シグナルを書き換えるために使用しない。

Block／Mute関係はprivate dataとし、相手へ不要に状態を明示しない。過去の正当なコメント、SCOUT履歴その他の既存履歴をBlock／Mute設定だけで遡及削除・改変しない。

### 読書表示設定（#3）

読者はエピソード読書画面で、文字サイズ、行間、明るい／暗い読書テーマ、本文横幅を選択できる。設定はallowlistされた表示プリセットとして端末内へ保存し、既定値へ戻せるようにする。

読書表示設定はpresentation-onlyとし、有効読書、作品Rank、LIGHT SEED、SCOUT、PV、露出、推薦、作者向け分析の判定を変更しない。未知または壊れた保存値は安全な既定値へ正規化する。

縦書き／横書き切替はこの基本機能へ自動的に含めず、需要、アクセシビリティ、本文記法、挿絵表示との整合を確認して別途判断する。

### クロスデバイス読書位置同期（#4）

未ログイン読者は端末ローカルの読書位置保存を利用し、ログイン読者は作品ごとの最小限の読書位置をアカウントへ同期できる。

同期データはprivate dataとし、本人だけが利用できる。後の話まで進んだ進捗を古い端末からの更新で巻き戻さず、同一話内の進捗も原則として単調増加させる。

読書再開位置は利便性データであり、有効読書、作品Rank、LIGHT SEED、Scout XPその他の評価証拠の代替にしない。同期失敗時も公開読書自体を壊さず、安全な端末ローカル状態へフォールバックできる構造を維持する。

### シリーズ機能（#5）

作者はシリーズ名、説明、作品の並び順を管理し、作品詳細から同一シリーズ内の前後作品へ移動できる。β版では1作品につき所属シリーズは最大1つを基本とし、1シリーズへ追加できる作品数には安全な上限を置く。

シリーズは作者の作品整理・読者ナビゲーション機能であり、シリーズ所属数、シリーズ内順位、シリーズ閲覧等を作品Rank、LIGHT SEED、SCOUT、PV、追加露出の直接加点へ利用しない。

一般読者へ表示するシリーズ情報は現在公開中の作品だけを基本とし、作者本人以外へ下書き作品や非公開情報を漏らさない。

### 章管理／章階層／エピソード並び替え（#6）

作者は作品内に章を作成・改名・削除し、エピソードを章へ所属させ、作品全体の順序を安全に変更できる。途中挿入や大量並び替えは、個々の話数を手作業で衝突させる方式ではなく、boundedなdatabase-side処理で原子的に確定する。

並び替え後もエピソードIDを維持し、同一作品内のepisode_number一意性を守る。章とエピソードの所属先作品が一致しない状態を許可しない。

一般読者向け目次は公開済みエピソードだけを返し、作者本人は管理目的で下書きを確認できる。章・並び順変更は本文改稿ではないため、それだけを理由に本文revisionを作らない。

### 誤字報告 → 作者確認 → 安全な適用（#7）

誤字報告は作品ごとの受信設定に従う作者向け補助機能とし、読者が本文の対象箇所と修正案を作者へ送れる。β版の既定受信状態はOFFとし、読者からの送信にはログインを必要とする。

対象箇所は現在の公開本文内で一意に特定できることを必要とし、重複提案、短時間大量送信、同一読者からの未処理提案数等へ上限を設ける。作者へは提案されたbefore／afterを見せるが、報告者の本人識別情報を不要に公開しない。

修正は作者の明示的な「適用」操作でのみ行い、自動修正しない。適用直前に現在本文、対象文字列、周辺文脈、所有権を再確認し、本文が変化して一致しない場合はstaleとして扱う。

適用時に変更してよいのは対象エピソードの本文だけを基本とし、エピソードID、話数、公開・予約状態、PV、作品Rank、LIGHT SEED、SCOUT、お気に入り、露出等を変更しない。適用前本文は改稿履歴へ残す。

### 改稿履歴／版管理／ロールバック（#8）

公開済み・保存済みエピソードのタイトルまたは本文を変更する場合、変更前の文章を作者本人専用の改稿履歴へ保存し、重大な誤編集から戻せるようにする。

β版では最新20 revision、90日間の閲覧可能保持を基本とする。復元は既存エピソード行のタイトルと本文だけを対象とし、エピソードID、話数、公開状態、予約状態、PV、Rank、LIGHT SEED、SCOUTその他の現在状態を過去へ巻き戻さない。

改稿履歴はprivate dataであり、一般読者へ過去版を常時公開する機能にはしない。

### 作者フォロー＋新作／更新通知（#9）

ログイン読者は作者をフォロー／解除でき、新作公開通知と第2話以降の更新通知を独立してON/OFFできる。フォロー開始時は現在までの公開イベントを基準点とし、過去作品・過去更新を大量に未読通知として流さない。

第1話公開は新作イベントとして扱い、同一公開を新作通知と更新通知の二重通知にしない。通知を一度OFFにした後で再度ONにした場合も、停止期間中の古いイベントを一斉配信しない。

Block／Muteの既存安全境界をフォロー・通知にも適用する。フォロワー数はβ版で人気指標として前面表示せず、作品Rank、LIGHT SEED、SCOUT、PV、検索順位、発見棚、追加露出へ直接加点しない。

### 本棚の高度整理（#10）

既存のお気に入りを別ライブラリへ複製せず、本人専用の本棚として拡張する。読者は作品を「あとで読む」「読書中」「読了」等に整理し、privateなリストラベルとメモを持てる。

本棚の状態、リスト名、メモは本人専用private dataとする。「読了」は読者本人の整理状態であり、NOVELIGHTが全話読了を客観認定した値として扱わない。

本棚整理はお気に入り、読書位置、更新通知と共存させるが、作品Rank、LIGHT SEED、SCOUT、検索順位、発見棚、露出その他の評価・発見ロジックへ直接使用しない。

### 作品ごとの受信・交流設定（#11）

作者はアカウント全体の交流受信既定値を持ち、作品単位で上書きできる。コメント受信と誤字報告受信は別設定として扱う。

β版の既定はコメントON、誤字報告OFFを基本とする。作品は作者既定値を継承でき、明示的な作品単位ON/OFFへ切り替えた後、再び作者既定へ戻すこともできる。

受信をOFFにしても既存コメント、既存誤字提案、過去の正当なSCOUT証拠等を削除しない。OFF中は新規受付だけを停止し、コメントの場合は既存コメントを読める状態を維持しつつ投稿UIを閉じる。

#12「ルビ・傍点等の小説向け本文表現」は第43章「安全な小説向け本文記法」を正式仕様とする。任意HTMLを許可せず、プレーンテキスト正本＋安全なpresentation変換を維持する。

#13「予約公開の複数話・範囲管理」は第43章「複数話の予約公開管理」を正式仕様とする。既存の予約公開Source of Truthとdue publication workerを維持し、batch変更は原子的に扱う。

### コメントの作者モデレーション強化（#14）

作者は自作品の可視読者コメントについて、β版では作品ごとに1件の固定、soft-hide／再表示、boundedな非表示理由、1コメントにつき1件の作者返信を管理できる。作者返信は編集・削除可能とする。

非表示は原コメント行を物理削除せず、過去の正当なSCOUT等の履歴証拠を改変しない。作者返信そのものへScout XPを付与しない。作者自身のコメントをモデレーション機能で固定・非表示して人気演出へ利用することも許可しない。

モデレーション操作はprivate auditとして記録可能とし、Block境界を尊重する。固定・非表示・作者返信は作品Rank、LIGHT SEED、SCOUT、PV、お気に入り、検索順位、発見棚、露出へ直接影響させない。

### ネタバレ表示（#15）

コメント等でネタバレを含む内容は投稿時にネタバレ指定でき、読者が明示的に開くまで本文やそれに付随する作者返信を初期非表示にできる。

ネタバレ指定は表示制御専用とし、作品Rank、LIGHT SEED、SCOUT、PV、お気に入り、発見・露出へ加点・減点しない。

登場人物一覧、目次、更新通知、本棚、読書再開等における未到達情報の先回り防止は第43章「登場人物の自動出現管理と読者向け一覧」のネタバレ境界も併せて適用する。


### #16〜#17の正式仕様

#16「限定公開／共有リンク」は第43章「下書き作品の限定公開／共有リンク」を正式仕様とする。限定共有中も作品はdraftをSource of Truthとし、通常の検索、Rank、LIGHT SEED、SCOUT、PV、お気に入り、発見・露出へ混入させない。

#17「読書履歴・個人読書統計」は第44章「本人専用の読書履歴・個人読書統計」を正式仕様とする。既存の有効読書証拠を本人向けpresentationとして再利用し、privateな読書履歴を作者や他ユーザーへ公開しない。

### 読み上げ（TTS）（#18）

エピソード本文の読み上げは、β版ではブラウザ／OS標準のWeb Speech APIを利用する。外部音声生成APIや新しい従量課金基盤をTTSの必須条件にしない。

読み上げは読者の明示操作で開始し、再生、一時停止、再開、停止を提供する。ページ表示だけで自動再生しない。日本語音声が利用可能な場合は優先し、端末側に存在しない場合はブラウザ／OSの安全なfallbackに従う。

読み上げ前に本文を安全な読み上げ用テキストへ正規化し、ルビ注釈等をそのまま重複読み上げしない。長文は安全な単位へ分割し、ページ移動・再mount等では読み上げを停止する。

TTSはpresentation-onlyとし、DB、RLS、作品Rank、LIGHT SEED、SCOUT、PV、推薦、検索順位、発見棚、作者向けLIGHT ANALYTICSへ影響させない。

Freeプランの投稿可能作品数は2作品とする。

Standardは10作品、Premiumは30作品を維持する。

Freeでも、既存作品と新作、長編と短編等を並行してNOVELIGHT上で試せる余地を持たせる。一方、Standard・Premiumとの投稿可能作品数の差は維持し、有料プランの価値を失わせない。

上限は料金ページ等の表示だけでなくdatabase-sideのauthoritative ruleとして強制し、同時投稿・複数タブ・直接API操作等によって3作品目を作成できない構造を必須とする。

### エピソードハート

既存のお気に入りと、エピソードハートは役割を分離する。

お気に入りは「この作品を継続して追いかけたい」という作品単位の意思表示とする。

エピソードハートは「この話が良かった」という各エピソードへの軽い好意的リアクションとする。作者がコメントを書くほどではない読者からも反応を受け取りやすくし、作者が書き続ける理由を増やすことを目的とする。

ハートはログイン済みユーザーだけが利用でき、1ユーザーにつき1エピソード1件までとする。同じエピソードのハートボタンを再度操作した場合は解除できる。

作者本人は自分のエピソードへハートできない。下書き・非公開エピソードへの一般読者ハートも許可しない。

ハート総数は読者・作者へ公開表示できる。個々のハート送信者を作者へ一覧公開する機能はβ版の必須範囲にしない。

database-sideのunique constraint等によって二重登録を防ぎ、連打、複数タブ、concurrencyによって同じユーザーの重複ハートが作られない構造にする。本人以外が他人のハートを削除・改変できない権限境界を持たせる。

Blockが成立している相手との直接リアクションは既存の直接交流境界と整合させる。Muteはpresentation機能として扱い、過去のハート履歴を遡及改変するために使用しない。

### ハートと評価・発見の分離

β版ではエピソードハート数を、作品Rank、LIGHT SEED、SCOUT RECORD、Scout XP、検索順位、発見棚、推薦順位、有料プランによる追加露出、新作48時間ブーストその他の評価・露出計算へ直接使用しない。

ハートを押すだけでScout XPを付与しない。相互ハート、複数アカウント、BOT、購入その他による水増しを作品成長へ変換できる設計にしない。

β期間中は独立した読者反応データとして利用率・ハート率・不自然な操作を計測し、将来ほかの制度へ利用するかは実データと不正リスクを確認してから別途決定する。

異常なハート行動は第13章の不正対応原則に従い、異常検知 → 記録 → 必要に応じた確認・警告 → 制限 → 悪質・反復時の停止を基本とする。自動検知だけを根拠に機械的な即BANを原則としない。

### エピソード本文内の挿絵

作者はエピソード本文の任意位置へ挿絵を配置できる。

挿絵は、場面イラスト、キャラクター、地図、設定資料、章扉その他、小説本文を補助する表現として扱う。挿絵の利用を作品投稿の必須条件にはせず、文章だけの作品も同等に投稿・閲覧できる状態を維持する。

β版では既存のプレーンテキスト本文を全面的なWYSIWYG／任意HTML文書へ置き換えない。既存episodes.contentとの後方互換性を維持し、本文中の安全な挿絵ブロックがNOVELIGHT管理下のillustration ID等を参照する構造を基本とする。

生HTML、script、event handler、iframe、任意の外部画像URLその他の自由埋め込みを本文機能として許可しない。読者表示時は、対象挿絵が当該エピソードへ正当に所属し、現在表示可能な状態であることを確認してから描画する。

作者Aが作者Bの挿絵IDを指定して流用する等の越権をdatabase-sideで防止する。

### 挿絵ファイルと表示仕様

β版で受け付ける画像形式はJPEG、PNG、WebPとする。

SVGとGIFはβ版では受け付けない。

1画像のアップロード時原本は最大10MB、1エピソード最大10枚をβ初期上限とする。上限値は運用・Storage費用・利用実態から将来調整可能とする。

β初期の入力画像は長辺4096pxまでを基本上限とし、読者配信用には長辺2000px以下を基本とした最適化画像を自動生成できる設計とする。元画像をそのまま全読者へ配信することを既定にしない。

NOVELIGHT側で表示速度と通信量を保つため、アップロード後にサイズ・容量・配信用形式等を自動最適化できる。最適化によって作品内容を意図的に改変する処理は行わない。

読者画面ではアスペクト比を維持し、PCでは本文コンテナを越えず、スマートフォンでは利用可能な本文幅へ収まるレスポンシブ表示を基本とする。

挿絵はlazy loadingを基本とし、可能な範囲で画像寸法等を事前に保持してCLSを抑制する。

作者はalt textを設定できる。装飾目的か内容理解に必要な画像かを考慮し、未入力時もアクセシビリティを壊す不適切な代替文を自動生成して断定しない。

### 挿絵Storage・権限・ライフサイクル

挿絵は作者ギャラリーや作品サムネイル素材と用途・公開境界が異なるため、既存Storageを安易に流用しない。挿絵専用の所有権・公開状態・エピソード所属を安全に判定できる構造を持たせる。

下書きエピソードへアップロードした挿絵は、Storage URLを知っているだけで一般公開できる状態にしない。作者本人と正当に権限を持つ編集経路だけが下書き挿絵へアクセスできることを基本とする。

公開エピソードの挿絵は、当該エピソードの公開条件・内容警告・年齢ゲートと整合した読者経路から表示する。作品・エピソードを非公開化した場合に、本文だけ非公開で画像だけ一般公開され続ける状態を避ける。

画像削除、差し替え、エピソード削除、作品削除、下書き破棄等によって参照されなくなったファイルは、安全な猶予・参照確認を経たうえでorphan cleanupできる構造にする。別の下書き、改稿履歴、共有中データ、バックアップ等がまだ参照している画像を誤って物理削除しない。

### 既存作者機能との整合

挿絵の追加によって、サーバー下書き、端末自動保存、公開前プレビュー、改稿履歴、複数話予約公開、章・並び順管理、共同執筆、限定共有、誤字報告、読書設定、TTS、内容警告、モバイル読書その他の既存機能を破壊しない。

改稿履歴では、本文が過去revisionへ戻った際に挿絵参照だけ壊れる状態を避ける。挿絵の参照関係とasset lifecycleを履歴保持期間と整合させる。

作者向け作品エクスポート／バックアップでは、挿絵を使用する作品について参照情報を黙って失わせない。TXTだけでは完全な画像バックアップを表現できない場合、manifest、ZIP等を含む拡張方式を設計し、少なくとも「本文は戻せるが挿絵構成は復元不能」という状態を完成仕様にしない。

共同執筆者が挿絵を操作できる範囲は既存editor権限を越えないよう別途権限確認する。挿絵追加を理由に作品公開、削除、課金、露出設定その他のowner-only権限を共同執筆者へ広げない。

TTSは挿絵自体を読み上げず、本文の読み上げを継続する。alt textをTTSへ自動挿入するかはアクセシビリティ実利用を確認して別途判断し、意図しない長文読み上げを強制しない。

### AI生成・AI支援挿絵

AIで生成・加工した画像も挿絵として使用可能とする。

AI画像を利用したことだけを理由に作品を不利に扱ったり、挿絵利用そのものを禁止したりしない。一方、AIで生成したことを理由に、著作権、商標、肖像、プライバシー、名誉その他第三者の権利、利用規約、投稿ガイドライン、外部AIサービスの利用条件が免除されることはない。

本文・作品制作についてのAI利用区分と、挿絵のAI利用は分離して扱う。作者本人が文章を執筆し、挿絵だけに画像生成AIを使用したことのみを理由として、その作品全体を「AI生成主体作品」と扱わない。

作品単位で「挿絵にAI生成・AI支援画像を含む」ことを別途保持・表示できる仕組みを設ける。作者は最初の挿絵アップロード時等に設定でき、後から変更可能とする。原則として画像1枚ごとに毎回同じ申告を強制し、投稿体験を過度に重くしない。

AI画像の異常検知を将来導入する場合も、第12章と同様に異常検知を運営確認の補助として扱い、自動判定だけを根拠に原則として自動BAN・自動削除しない。

### 挿絵の権利・成人向け・過激表現

挿絵は作品本文の一部であり、利用規約、投稿ガイドライン、著作権・権利保護、通報、年齢区分、内容警告、ゾーニングの対象とする。

作者は、自分が利用する権利を持つ画像だけを投稿する。他人が制作した画像の無断転載、著作権・商標権・肖像権・プライバシーその他第三者の権利を侵害する画像は禁止する。

R18・成人向け・性的表現は第30章に従う。成熟したテーマ等は必要に応じて警告・年齢区分・ゾーニングで扱うが、β版でStripeを利用している間、性的満足を主目的とする露骨な性的・ポルノグラフィックな画像は、年齢警告を付けても投稿できない。

過度な残虐表現・グロテスクな画像も、作品の内容警告・ゾーニングと整合させる。法令、決済事業者、ホスティングサービスその他の外部規約に抵触する内容は投稿できない。

### 政治・実在人物・誹謗中傷を含む挿絵

政治、選挙、政治家、社会問題等を題材とすること自体は一律禁止しない。

ただし、実在人物になりすます画像、記録写真・実際の出来事であると読者に誤認させることを目的とした欺瞞的な合成・生成画像、肖像権・プライバシーその他の権利を侵害する画像、特定の個人・団体への嫌がらせ・誹謗中傷・名誉を傷つけることを目的とする画像は投稿ガイドライン上の制限・禁止対象とする。

風刺、フィクション、批評その他の表現を政治題材であることだけを理由に自動禁止しない。一方、フィクション表示やAI生成表示が存在しても、それによって権利侵害、嫌がらせ、誹謗中傷その他の禁止行為が許可されるわけではない。

政治・実在人物を扱う画像の安全基準は、特定の思想・政党・候補者への賛否で有利不利を変えず、同一の権利・安全基準を中立に適用する。

### 通報・モデレーション

読者は本文挿絵について、著作権侵害、無断転載、禁止コンテンツ、嫌がらせ・権利侵害、その他投稿ガイドライン違反を既存の通報導線から報告できるようにする。

画像だけを利用して本文の年齢区分・内容警告・禁止コンテンツ判定を回避できる設計にしない。

通報や自動検知があった場合も、重大な安全・法的問題を除き、第14章の段階的対応を基本とする。必要に応じて画像単位の非表示・削除、作品制限、作者への確認等を行える構造にする。


### 挿絵アップロード時の注意表示

アップロード画面では、作者が毎回長文を読まなくても重要事項を認識できるよう、短い注意書きを常時表示し、「詳しいルール」から詳細を展開できる構成を基本とする。

短縮表示の基本文言は以下とする。

「AI生成画像も使用できます。権利侵害・無断転載・誹謗中傷・禁止される成人向け表現・政治家等について事実と誤認させる画像は禁止です。挿絵は投稿ガイドライン・通報・ゾーニングの対象です。」

詳細表示では、少なくとも以下を明示する。

- JPEG・PNG・WebP形式の画像を利用でき、AIで生成・加工した画像も利用できること
- 投稿できるのは作者が利用する権利を持つ画像に限ること
- 他人の画像の無断転載、既存作品・キャラクター・ロゴ等の権利侵害、実在人物の肖像権・プライバシー侵害を禁止すること
- 特定の個人・団体への誹謗中傷、嫌がらせ、名誉を傷つける目的の画像を禁止すること
- R18・成人向け・性的表現、残虐・グロテスク表現はNOVELIGHTの年齢区分・内容警告・禁止基準に従うこと
- 政治・選挙・政治家・社会問題を題材にすること自体は禁止しないが、なりすまし、事実と誤認させる欺瞞的合成、権利侵害、誹謗中傷等は禁止すること
- AI生成画像も利用したサービスの規約、第三者の権利、NOVELIGHTの投稿ルールの対象であり、AI生成であることは免責理由にならないこと
- 挿絵は作品本文の一部として、通報、年齢区分、内容警告、投稿ガイドラインの対象になること
- 表示速度を保つため、NOVELIGHT側で画像のサイズ・容量等を自動最適化する場合があること

注意書きは、合法な創作・政治的題材・AI利用そのものを萎縮させるためではなく、作者が投稿前に権利・安全・ゾーニング上の重要条件を確認できることを目的とする。

### 本章の運用原則

Free 2作品、エピソードハート、本文挿絵はいずれも、機能数を増やすこと自体を目的としない。

Free 2作品は作者がNOVELIGHTを実際に試し続けられる余地、ハートは作者へ軽い反応が届く継続理由、挿絵は作品表現の幅を広げることを目的とする。

β公開後は利用率、継続率、Storage・通信コスト、不正、通報、読書体験への影響を計測し、上限値・UI・最適化方式等の手段は必要に応じて調整する。ただし、課金で評価そのものを買わせないこと、権利・安全を守ること、作者と読者が長く小説を続けられる環境を作ることは維持する。


## 47. NOVELIGHT AI / AI創作・読書・作品発見・運営支援基盤

本章は、正式リリース以降のNOVELIGHTにおける重要な差別化軸として、「AI × 投稿 × 実読者データ × 作品発見」を統合する長期方針を定める。

NOVELIGHT AIは単独の「AIレビュー機能」ではない。AI創作支援、AI作品管理、AI作品分析、AI Analytics、AI読者支援、AI作品発見、AI宣伝支援、AI運営支援を共通AI基盤上で段階的に拡張する上位概念とする。

最終的には、

書く
→ 整える
→ 投稿する
→ 読まれる
→ 実読者データを取得する
→ AIで分析する
→ 改善する
→ さらに書く

という創作サイクルをNOVELIGHT内部で完結できる状態を目指す。

NOVELIGHTを「投稿サイトにAI機能が付いているサービス」で終わらせず、「投稿・執筆・分析・作品発見・読書をAIと実読者データで統合した小説プラットフォーム」へ発展させる。

### 正式採用範囲と変更可能範囲

本章で整理するAI機能群は、中長期ロードマップ上の正式な採用候補として原則すべて保持する。

ただし、すべてを正式リリース初日に完成させることは要求しない。共通基盤を先に構築し、価値・品質・原価・安全性・実利用データを確認しながら高価値な機能から段階的に公開する。

各機能の実装順、詳細仕様、UI、使用モデル、使用プロバイダー、Credit消費量、プラン内包量、価格その他の手段は、実データ、AI原価、品質、競合状況、法務・外部規約等から変更可能とする。

機能数そのものを成功指標にしない。「AI機能が何個あるか」ではなく、作者が書き続けやすくなるか、作品改善がしやすくなるか、読者が作品を理解・発見しやすくなるか、運営負担を減らせるかで評価する。

### β版・正式リリースとの関係

2026年9月30日のβ版公開時点では、本章のNOVELIGHT AI共通基盤およびAI機能群を実装しない。

AIの本格開発はβ公開後の別workstreamとして開始する。β公開前作業へ混在させず、公開直前にAI基盤を追加してProductionリスクを増やさない。

β期間中から「正式リリースに向けてNOVELIGHT AIを開発予定」であることは積極的に告知し、正式リリース時の大型アップデート群として期待を作る。

ただし、未実装機能を実装済み・利用可能と表現せず、確定していない公開日を断定しない。

正式リリース時にはNOVELIGHT AIを重要な差別化軸として扱うが、全機能一斉公開を完成条件にはしない。正式リリース前後を通じて段階的に拡張してよい。

### 1. AI作品分析

長編作品全体、エピソード単位、ストーリー構成、プロット、ペーシング、読みやすさ、文体、POV／視点ブレ、感情曲線等を分析できるようにする。

良かった点、改善候補、改善優先順位、続きを読みたくなる要素、作品テーマ、序盤・中盤・終盤のバランス、更新前後比較、過去分析比較、作者成長等も扱う。

単発のAI感想ではなく、作品全体を継続的に理解し、過去の分析と接続できる仕組みを目指す。

### 2. AI作品カルテ / Novel Bible

作品カルテをNOVELIGHT AIの中心基盤とする。

作品ごとに、登場人物、年齢、性格、特徴、口調、一人称、能力、所属、人物関係、地名、組織、世界設定、魔法・能力体系、アイテム、重要事件、時系列、現在位置、生存・死亡、秘密、伏線、回収済み伏線、未回収伏線候補、作品テーマ、ストーリーライン等を構造化して保持できるようにする。

新エピソード投稿時は、可能な限り新規・変更部分と必要な周辺文脈だけを解析し、既存作品カルテへ差分統合する。

第43章の既存登場人物レジストリや作者用プロット・キャラクター・世界観ノートと統合し、ユーザー向けに第二・第三の人物台帳を乱立させない。

### 3. AIキャラクター・設定管理

登場人物自動抽出、直近登場話数、登場頻度、人物関係、キャラクター変化追跡、口調ブレ、性格ブレ、一人称ブレ、能力矛盾、設定矛盾、名前表記揺れ、年齢矛盾、キャラクター位置矛盾、設定変更検出、世界観整合性等を支援する。

AIが抽出・推測した内容と、作者が明示的に登録・修正した正式設定を区別できる構造を持たせる。

### 4. AI伏線・時系列・矛盾管理

伏線候補、最後に登場した話数、回収済み候補、未回収候補、長期間放置候補、時系列矛盾、キャラクター行動矛盾、年齢矛盾、季節・時間帯矛盾、移動時間矛盾、世界設定矛盾等を確認できるようにする。

AIは原則として「間違い」と断定せず、「確認候補」「矛盾の可能性」等として提示し、作者の意図した演出・叙述トリック・未公開設定を誤って否定しない。

### 5. AI執筆アシスト

誤字脱字、文法、不自然な日本語、冗長表現、言い換え、短文化、詳細化、描写強化、情景描写、五感描写、Show, not tell候補、セリフ改善、キャラクター口調維持、地の文改善、文体統一、シーン改善等を支援する。

展開候補、プロット相談、次の展開候補、名前候補、地名候補、能力名候補、アイテム名候補、タイトル候補等も扱えるようにする。

AIが本文を勝手に変更するのではなく、作者へ候補を提示し、採用・修正・不採用の最終判断は作者が行う。

### 6. AI投稿前チェック

公開直前に、誤字脱字、表記揺れ、一人称ブレ、キャラクター設定矛盾、世界設定矛盾、時系列矛盾候補、フォーマット異常、重複表現、タイトル、あらすじ、タグ候補、内容警告候補等を確認できるようにする。

原則として警告・提案であり、AI判断だけを理由に投稿を禁止しない。

既存の公開チェック等の公開前確認と重複する場合は別機能を増やさず、AIを必要とする高度確認だけを同じ公開前導線へ統合する。

### 7. AIあらすじ・紹介・宣伝支援

短いあらすじ、長いあらすじ、50文字紹介、150文字紹介、キャッチコピー、タイトル案、タグ案、ジャンル候補、X投稿、更新告知、完結告知、新作告知、作者近況、作品紹介、読者向け紹介、出版社向け紹介等を生成できるようにする。

第43章の作者近況・更新ノート等、既存の作者発信機能と自然に連携させる。

### 8. AI Analytics Copilot

NOVELIGHTの重要な独自差別化機能として、AI作品分析と実読者データを統合する。

使用候補データには、PV、第1話到達率、各話継続率、離脱率、読了率、お気に入り率、LIGHT SEED、再訪率、流入元、曜日、時間帯、更新前後比較等を含む。

例えば「第3話で説明文比率が上昇した」というAI側の内容分析と、「第3話から第4話で実際の離脱率が上昇した」という実測を照合し、作者へ改善仮説を提示できるようにする。

AIによる推測、統計上の相関、実際に観測された読者行動を明確に区別し、因果関係を断定しない。

### 9. AI読者離脱解析

離脱地点について、会話量、説明量、文字数、登場人物数、場面転換、戦闘、新設定、主人公不在、テンポ、感情曲線等を分析し、離脱理由の候補を作者へ提示する。

AI推測と実測データを明確に分け、読者個人を特定する分析ではなく、必要に応じて匿名化・集計された行動データを使用する。

### 10. AIターゲット読者分析

作品内容と匿名化・集計された実読者行動から、どの読者傾向と相性が良いかを分析する。

AIだけの推測より、NOVELIGHT内の実読者データによる検証・補強を重視する。

### 11. AI Virtual Beta Reader

複数の疑似読者視点から、興味を持つ地点、退屈する可能性がある地点、キャラクター印象、分かりにくい地点、続きを読みたい要因等を提示する。

Virtual Beta Readerの出力は人間読者の感想・レビュー・実読者データと明確に分離し、人間読者が実際にそう感じたかのように表示しない。

### 12. AI自然文作品検索

「主人公が最初弱くて徐々に強くなる学園ファンタジー」等の自然文から、内容・読者との相性を使って作品を探せる仕組みへ発展させる。

第44章の「自然文で探す β」は、β版では外部LLM・Embedding APIを必須にしない説明可能な決定論的検索として維持する。本項はβ公開後に、その安全境界と説明可能性を守りながら意味検索・対話的絞り込み等へ拡張する将来仕様とする。

人気・課金・AIによる作品品質評価を、自然文関連度へ無関係に加算しない。

### 13. AIおすすめ / LIGHT SEED発見支援

AIは作品の価値そのものを判定せず、読者と作品の内容上の相性、新しい作品との出会い等を支援する。

AIが作品へLIGHT SEEDを付与することは禁止する。AIの品質スコアを作品RankやLIGHT SEEDへ加算しない。

AIによる推薦を利用する場合も、「この作品は優れている」という評価ではなく、読者の希望・作品内容との適合や発見支援として扱う。

### 14. AI「この人物誰だっけ？」

読者が現在到達している範囲までの情報だけを使用して、キャラクターの役割、関係、過去の登場等を説明する。

現在読了位置より未来の話、未到達の秘密、後の人物関係等を回答へ混入させない。

### 15. AIネタバレ防止おさらい

前回までのあらすじ、キャラクター、人物関係、世界観、現在の目的、重要イベント等を、読者が到達済みの範囲だけから生成する。

長編へ戻りやすくすることを目的とし、未来話の本文・タイトル・設定等を先回りして要約しない。

### 16. AI作品用語集

作品カルテから、人物、地名、組織、魔法、能力、アイテム、専門用語等を整理して読者・作者を支援する。

読者向け表示では未到達情報を出さず、作者向けの完全な作品カルテと読者向けのネタバレ安全な用語集を分離する。

### 17. AIサムネイルコーディネーター

Geometry Thumbnail Engineと連携し、AI画像生成そのものではなく、NOVELIGHT公式素材から作品内容に合う組み合わせを推薦する。

現在の正式作者向けカテゴリは第39・40章に従い、背景、基準本、背景模様、中央シンボル、枠を対象とする。

過去案に含まれていたcover_textureやeffect等、第39・40章で作者向け描画から廃止・非採用となったレイヤーを、本項を理由に復活させない。将来MASTER側で公式カテゴリが変更された場合は、その時点の正式カテゴリへ追従する。

UIは「自分で選ぶ」「おまかせで選ぶ」「AIにおまかせ」等を候補とし、AIが任意画像・任意URL・非公式素材を差し込める構造にはしない。

### 18. AIタイトル・あらすじA/Bテスト

AIが複数のタイトル・あらすじ等の候補を生成し、作者の明示許可により一定期間テストできるようにする。

表示から作品クリックへの転換等を比較できるようにするが、AIが勝手に恒久変更しない。

テスト結果も作品Rank、読者評価、LIGHT SEED等の人間評価そのものとして扱わない。

### 19. AIコメント要約

多数のコメントについて、好評点、不満点、質問、ネタバレ、よく出る話題等をまとめ、作者が読者反応を把握しやすくする。

少数意見を多数意見と誤認させず、必要に応じて集計対象・件数等を確認できる設計を目指す。

### 20. AIコメント返信支援

作者へコメント返信候補を提示できるようにする。

AIが作者本人のふりをして勝手に投稿せず、最終送信は作者の意思で行う。

### 21. AIネタバレコメント検知

コメント位置や読者到達範囲等と照合し、未来情報を含む可能性があるコメントを検出して、警告・折りたたみ等へ利用できるようにする。

AI判定だけでコメントを恒久削除せず、誤検知を前提に安全な表示制御・人間確認と組み合わせる。

### 22. AI作者成長レポート

過去との比較から、文体、読了率、会話比率、文の長さ、キャラクター一貫性、構成、読者継続率等の変化を提示する。

単なる作品間ランキングではなく、作者自身の過去との比較と改善材料を中心にする。

### 23. AI出版準備

長編あらすじ、企画書、キャラクター紹介、世界観資料、シリーズ構成、章構成、想定読者、実読者データ、編集者向けサマリー等を整理できるようにする。

NOVELIGHT発の書籍化支援へ利用可能とするが、第32章の出版事業そのものの保留方針を自動的に解除するものではない。

### 24. AI翻訳

将来の海外展開時に、作品カルテを利用してキャラクター口調、固有名詞、世界観、魔法名称等の整合性を保った翻訳を目指す。

海外展開自体は第32章の保留方針に従い、本項だけを理由に海外展開開始を確定しない。

### 25. AI音声読み上げ

第45章のβ版ブラウザ／OS標準TTSはそのまま維持する。

本項は、将来のAI音声生成、キャラクター表現、より高度な音声体験等への拡張候補とし、既存TTSを置き換える必須要件にはしない。

AI原価、音声権利、成人向け作品、外部サービス規約等の影響が大きいため、優先度は低く扱う。

### 26〜35. 運営向けAI

以下を原則採用候補として保持する。

26. AIコメントモデレーション補助
27. AI通報分類・要約
28. AI不正検知支援
29. AI作品分類異常検知
30. AI盗作・類似作品検知補助
31. AI規約違反候補検出
32. AI問い合わせ分類・回答支援
33. NOVELIGHT正式仕様に基づくAI FAQ
34. AI障害・ログ要約
35. AI KPI異常検知

運営AIは、人間の最終判断を置き換えるためではなく、少人数運営で確認すべき対象を絞り、情報整理を高速化するために使う。

第14章の「異常検知 → 記録 → 必要に応じて確認・警告 → 制限 → 悪質・反復の場合は停止」という基本原則を維持し、AIだけでBAN、削除、重大な権限制限その他の重大措置を決定しない。

### 共通AI基盤を最優先する

上記の多数の機能を完全に独立した35個以上のシステムとして作らない。

最低限の共通基盤候補は以下とする。

- 作品カルテ / Novel Bible
- AI Router
- プロバイダー抽象化
- モデル抽象化
- 差分解析
- キャッシュ
- 分析結果保存
- AI Credit
- AI原価計測
- フォールバック
- 共通作品データ
- 共通読者データ
- 共通セキュリティ
- 共通監査ログ

共通基盤を高品質で作り、その上から各機能を派生させる。

AI関連開発は数か月単位で段階的に進めることを前提とし、機能数を急いで増やすために基盤品質を犠牲にしない。

### 複数AIの役割分担

NOVELIGHT AIは、1種類の高性能AIですべてを処理する方式を基本としない。

軽量・低価格AIは、誤字、分類、要約、タグ、固有名詞抽出等へ利用する。

中性能AIは、キャラクター分析、設定分析、伏線、矛盾、構成等へ利用する。

高性能AIは、長編総合分析、複雑な改善提案、複数情報の統合等、必要品質が高い処理へ限定して利用する。

将来的なNOVELIGHT専用AI・専用モデルも選択肢として保持する。

### 複数AIプロバイダーとAI Router

候補プロバイダーには、OpenAI、Anthropic、Google、その他将来のAI、オープンモデル、将来のNOVELIGHT専用モデル等を含む。

特定の1社へ強く依存せず、同じNOVELIGHT機能でも、品質、価格、速度、コンテキスト長、障害状況、データ取扱条件等から使用モデルを変更可能にする。

AI Routerは「常に最も高性能なモデルを使う」仕組みではなく、「必要品質を満たす中で最も合理的なモデルを選ぶ」仕組みとする。

目標は、

同じ品質なら最安
または
同じ原価なら最高品質

とする。

プロバイダー切替やフォールバックによって、単一企業の障害・値上げ・仕様変更でNOVELIGHT AI全体が停止・赤字化しにくい構造を目指す。

### 差分解析・キャッシュ・長期記憶

分析済み作品を毎回全文再解析する方式を基本としない。

例えば第1〜50話を分析済みで第51話が追加された場合、第51話と必要な関連情報を中心に解析し、既存作品カルテへ統合する。

長編になるほど継続利用原価が無制限に増えない構造を目指す。

同一・類似要求で再利用可能な結果はキャッシュし、作品カルテ、構造化データ、過去分析結果を共通資産として再利用する。

ただし、古い分析結果を無条件に使い続けず、作品更新・設定変更・モデル変更等によって再解析が必要な範囲を判定できるようにする。

### AI原価最小化

NOVELIGHT AIでは、品質を維持しながらAI原価を可能な限り小さくすることを最重要設計原則の1つとする。

原価削減候補には、軽量AI、AI Router、複数プロバイダー比較、差分解析、キャッシュ、バッチ処理、作品カルテ再利用、構造化データ、出力token削減、不要なAI呼び出し削減、重複処理防止、小型モデル、将来の専用モデル等を含む。

高性能AIへ毎回作品全文を送るような構造にはしない。

AI機能の数が増えただけで大量のAPI原価が自動発生する構造にもせず、原則としてユーザーが実行したAI処理、または必要性が明確な自動処理に対して原価が発生する設計とする。

投稿時等に自動で動くAIは特に原価へ注意し、常時高性能AIを動かさず、ルール処理、差分、軽量AI、バッチ等を優先する。

### AI原価目標

標準的なAI処理について、1 AI Creditあたりの平均AI原価を数円〜10円程度へ可能な限り抑えることを技術目標とする。

これは品質や将来の外部価格を無視した絶対保証値ではない。

原価が想定以上の場合、ユーザー価格の値上げより先に、モデル変更、プロバイダー変更、Router変更、キャッシュ、差分解析、バッチ、処理圧縮、小型モデル、専用AI等による改善を検討する。

### AI利用原価の計測

可能な範囲で、AI機能、作品、処理種別、プロバイダー、モデル、入力token、出力token、キャッシュ利用、API原価、Credit消費、AI関連売上、粗利等を記録する。

「AI全体でいくら使ったか」だけではなく、どの機能・モデル・処理が高いか、どの機能が継続利用されているかを把握できるようにする。

個人情報・作品本文等を原価分析用ログへ不必要に複製せず、計測目的に必要な最小情報へ分離する。

### AI Credit

高負荷AI機能についてはAI Creditによる利用管理を基本とする。

すべての小さなAI処理へCreditを要求する必要はない。

基本構造候補は、

Free
→ 初回体験

Standard
→ 一定量の軽量AI・少量AI利用を含む

Premium
→ Standardより多いAI利用を含む

追加利用
→ AI Credit購入

とする。

軽量AIはStandard / Premium内で一定量利用可能にし、高負荷AIはAI Creditを消費する方式を基本候補とする。

ユーザーUIでは過度に細かい小数Creditを見せず、「プラン内」「1 Credit」「2 Credits」「3 Credits」等の理解しやすい単位を優先する。

### AI Credit価格候補

現時点の価格候補は以下とする。

3 Credits：税込660円
10 Credits：税込1,980円
30 Credits：税込4,980円

これは正式確定価格ではない。

正式リリース前に、実AI原価、決済手数料、インフラ費、競合相場、AI品質、外部AI価格、将来の値上げリスク等を確認して正式決定する。

目標価格帯は競合AI創作支援サービスより若干安い程度を基本とし、極端な安売りは行わない。

第25章の読者課金なし原則は維持する。AI Creditの導入を理由に、基礎的な作品発見・読書体験を有料化しない。

### 価格の長期安定

可能な限り、一度ユーザーへ提示したAI関連料金を後から値上げしなくて済む設計を目指す。

外部AI事業者の価格上昇があった場合も、すぐユーザー価格へ転嫁するのではなく、AI Router、モデル変更、プロバイダー変更、キャッシュ、差分解析、小型モデル、専用AI等による吸収を優先する。

ただし、品質・安全性・事業継続を壊してまで価格を固定するという意味ではなく、重大な環境変化がある場合は透明性原則に従って再評価する。

### AIと人間評価の分離

AI分析結果を、作品Rank、LIGHT SEED、お気に入り、☆評価、読者評価、検索順位、課金露出等へ直接加算しない。

AIが高く評価した作品だから作品Rankやランキングを上げる仕組みにはしない。

作品の最終評価は人間読者へ委ねる。

自然文検索やおすすめでAIを利用する場合も、作品内容と検索意図・読者嗜好との適合を扱うものであり、「AIが作品品質を高く採点したから上位へ出す」という品質評価ロジックにはしない。

### 原則採用しないAI用途

以下は原則として採用しない。

- AIによる☆評価
- AI評価の作品Rank・ランキング反映
- AIによるLIGHT SEED付与
- AI読者BOTによるPV水増し
- AIが人間読者を装ってコメントすること
- AIレビューを人間レビューとして表示すること
- 作者確認なしで本文を自動改変すること
- AI判定のみでBAN・削除等の重大措置を行うこと
- AI大量生成作品をNOVELIGHTの中心機能にすること

AIは人間の創作・読書・評価を置き換えるためではなく、支援するために利用する。

### 作者作品・読者データ・外部AIの扱い

外部AIへ作品本文、作者データ、読者行動その他NOVELIGHTデータを送る場合は、利用規約、プライバシーポリシー、外部AI事業者のデータ利用条件、保存期間、学習利用、著作権、越境移転その他必要な条件を確認する。

第29章の「作品の権利は作者のもの」という原則を維持する。

NOVELIGHT専用AIの学習に作者作品を利用する場合も、利用許諾、オプトアウト、データ利用条件等を明確にし、投稿作品の無条件な学習転用を前提にしない。

読者行動をAI Analytics等へ利用する場合は、個人を不必要に特定せず、目的に応じて匿名化・集計・最小化を行う。

AI Routerは価格だけでなく、各プロバイダーのデータ取扱条件もルーティング条件として扱う。

### 競合AI機能の積極研究・採用

第42章の一般的な競合機能採用原則をAI領域にも明確に適用する。

小説投稿サイト、AI創作サービス、文章支援サービスその他関連サービスに有用なAI機能が存在する場合、「他社が先にやっているから」という理由だけで採用を避けず、積極的に研究する。

コピーするのは「ユーザーのどの課題を解決しているか」という機能思想・課題解決の考え方である。

他社のソースコード、固有文言、固有デザイン、独自名称、画像・素材、著作物、非公開アルゴリズム、非公開データ等をそのままコピーしない。

### 競合機能は＋α / 上位互換を目指す

他社と同等のAI機能を採用する場合、可能な限りNOVELIGHT独自の付加価値を加える。

少なくとも以下のいずれかを検討する。

1. NOVELIGHT実読者データとの統合
2. 作品カルテとの統合
3. 作者の操作負担削減
4. 差分解析・自動追跡
5. 長期記憶
6. 実読者反応との比較
7. LIGHT SEED・作品発見との統合
8. LIGHT ANALYTICSとの統合

## 48. 作品分類・公式タグ・自由タグ・検索属性基盤（2026-09-20正式方針）

### 48.1 目的

NOVELIGHTの作品分類は、メインジャンルを無制限に増やす方式ではなく、役割の異なる属性を分離した多層構造とする。

百合／GL、BL、TS／性別転換、ダンジョン配信、悪役令嬢、主人公最強等の横断的な特徴は、メインジャンルではなく公式タグで表現する。

この構造により、作者の投稿負担を抑えつつ、読者の複合条件検索、自然文検索、将来のAI作品発見へ拡張できる基盤を作る。

### 48.2 正式な6層構造

作品分類は以下の6層を正式基準とする。

1. メインジャンル
2. NOVELIGHT公式タグ
3. 作者自由タグ
4. 作品メタデータ
5. コンテンツ属性・内容警告
6. 将来のAI／検索内部属性

各層は目的を混同せず、同一概念を複数層へ無秩序に重複させない。

### 48.3 メインジャンル

メインジャンルは作品ごとに1つとし、β版の正式候補は以下の10種類を維持する。

- 異世界ファンタジー
- 現代ファンタジー
- 恋愛
- ラブコメ
- SF
- ミステリー
- ホラー
- 歴史
- 現代ドラマ
- その他

百合／GL、BL等を理由にメインジャンルを増殖させない。

### 48.4 NOVELIGHT公式タグ

公式タグはNOVELIGHTが意味を管理するcanonical taxonomyとする。

1作品につき最大10個まで作者が選択できる。

公式タグは安定した内部ID、表示名、主カテゴリ、表示順、aliasを持つ。

表示名を将来変更しても、一度公開した内部IDを別概念へ再利用しない。

同義語・表記揺れは新規タグを乱立させずaliasへ集約する。

初期canonical taxonomyの正本は `docs/novelight-tag-taxonomy.md` とし、本章はその運用原則を定める。

特に以下は横断公式タグとして正式採用する。

- 百合／GL
- BL
- TS／性別転換

百合／GLの代表aliasには「百合」「GL」「ガールズラブ」を含める。

BLの代表aliasには「ボーイズラブ」を含める。

TS／性別転換の代表aliasには「TS」「TSF」「性転換」「性別転換」を含める。

公式タグ候補は恋愛・関係性、Web小説定番、能力・バトル、ファンタジー、ダンジョン・ゲーム、SF、ミステリー・犯罪、ホラー、学園・青春、日常・仕事、歴史、雰囲気等へ整理する。

同じ概念が複数カテゴリ候補に現れる場合もcanonical tag自体は1件とし、主カテゴリを1つ定める。

### 48.5 作者自由タグ

作者自由タグは公式タグに存在しないニッチな特徴を補うための層とする。

1作品につき最大5個、1タグ30文字以内を基本とする。

空文字、重複、危険な制御文字・HTML境界を壊す入力等は拒否する。

公式タグまたはそのaliasと同一の自由タグは作成せず、公式タグへ誘導する。

自由タグは作者が作品を説明する補助情報であり、運営公式分類として扱わない。

将来、利用実績の多い自由タグを公式タグへ昇格させる場合は、alias・移行方針・既存作品との互換性を確認して別workstreamで行う。

### 48.6 作品メタデータ

公開状態、公開日時、更新日時、完結状態、エピソード数、AI利用区分その他の客観的な作品状態はメタデータとして扱う。

これらを雰囲気・関係性・題材等の公式タグへ無理に置き換えない。

既存の作品状態管理を正本とし、本章追加を理由に重複テーブルを作らない。

### 48.7 コンテンツ属性・内容警告

`content_rating`、`content_warnings` 等の安全・ゾーニング情報は公式タグ・自由タグから分離する。

「暴力」「流血」「性的テーマ」「自傷・自殺テーマ」等の警告は、作品発見用の嗜好タグではなく安全情報である。

作者が検索露出目的で内容警告を外したり、通常タグで代用したりする設計にしない。

既存の公開時DBガードを維持する。

### 48.8 将来のAI／検索内部属性

作品本文・構造・読者行動等から将来生成する検索補助属性は、作者向け公式タグとは別の内部属性として扱う。

内部属性は一般クライアントから直接読み書きできないことを基本とする。

AIによる自動分類、LLM作品解析、AIレビュー、AI Credit、AI Router等は2026年9月30日のβ公開後の別workstreamとする。

本章追加時点では、自動AI分類を有効化しない。

### 48.9 検索仕様

読者はメインジャンルと複数公式タグを組み合わせて検索できる。

β版の複数公式タグ選択はAND検索を標準とし、選択したすべての公式タグを含む作品のみ対象とする。

例：
- 百合／GL
- 異世界ファンタジー ＋ 百合／GL
- 異世界ファンタジー ＋ 百合／GL ＋ スローライフ

タグ条件を使用する検索では、課金プラン、作品Rank、LIGHT SEED、PVをタグ関連度へ直接加点しない。

自然文検索では公式タグの表示名・aliasを利用して検索意図を解釈できる。

「百合」「GL」「ガールズラブ」は同一の公式タグへ解決できる状態を維持する。

自然文検索も「AIが品質を高く評価した作品を上位にする」用途にはしない。

自由タグはキーワード検索対象へ含めることができるが、公式タグの代替taxonomyとして扱わない。

検索カードは情報過多を避けるため代表公式タグのみを表示し、作品詳細では設定された公式タグと自由タグを確認できる。

### 48.10 DB・権限境界

公式タグmasterは一般作者・読者から変更できない。

作品へのタグ紐付けは当該作品の作者本人だけが変更できる。

draft作品のタグは一般公開しない。

タグ保存は作品所有権、個数上限、重複、公式タグ存在確認をDB境界でも検証する。

クライアントUIだけを信頼しない。

公式タグ・自由タグは作品削除時にcascadeで削除できる設計とする。

将来AI用内部属性は一般クライアントへSELECT/INSERT/UPDATE/DELETE権限を付与しない。

### 48.11 既存作品との互換性

本基盤導入前の既存作品は、公式タグ0件・自由タグ0件でも正常に公開・表示・検索できることを必須とする。

既存作品へ推測でタグを自動付与しない。

作者が後から編集画面でタグを追加できる。

### 48.12 評価・露出との分離

公式タグ・自由タグの数そのものを作品Rank、ランキング、LIGHT SEED、SCOUT、PV、お気に入り、課金露出の加点要素にしない。

タグを大量設定した作品が有利になる構造を作らない。

検索条件への一致と、作品の人間評価・露出評価は別問題として扱う。

### 48.13 本章追加workstreamの実装範囲

本章追加workstreamでは、公式タグtaxonomy、alias、作者自由タグ、投稿・編集UI、作品詳細表示、公式タグAND検索、自然文検索への公式タグ統合、DB/RLS/rollback/testを実装対象とする。

AI自動分類、AI内部属性の自動生成、LLM API接続、AIレビュー、AI Router、AI Creditは実装しない。

Production DB変更は既存の本番承認境界を維持し、承認前に適用しない。

## 49. SCOUT RECORD本実装・称号・Scout Point正式方針（2026-09-21 / 名称更新 2026-09-24）

本章は、SCOUT RECORD本実装、Scout XP、Scout Point、読者称号、作者称号、限定称号、β版Level Cap、表示範囲、Point Ledger、不正対応、KPIおよびUI方向について正式方針を定める。

2026年9月24日の名称更新により、ユーザー向け「Badge」表記は原則として「称号」へ変更する。内部DB・RPC・badge_id等は互換性維持のため旧Badge名称を保持してよい。

本章は、第3章、第15章、第22章、第34章、第38章、第41章のSCOUT RECORD関連記述と一体で運用する。旧記述と本章が矛盾する場合、2026年9月21日以降のSCOUT RECORD本実装に関する具体仕様は本章を優先する。

本章追加workstreamではMASTER更新だけを行い、SCOUT RECORD本体、DB migration、Production mutation、Supabase変更、UI実装、AI Credit交換その他の実装には着手しない。

### 49.1 SCOUT RECORDの位置付け

SCOUT RECORDはNOVELIGHTの読者向け主要機能として本実装する。

目的は単なる実績収集ではない。

- 読者が新しい作品を探す理由を増やす
- 無名・新規作品を発掘する行動そのものを楽しくする
- 読者の継続利用を増やす
- 作者の「評価される前の機会」を増やす
- LIGHT SEEDと作品発掘をNOVELIGHT独自の体験として成立させる

ゲームをするためだけに作品を読む設計にはしない。

読書、発掘、評価、成長という本来の行動をゲーミフィケーションによって補強する。

人気SCOUTの評価、称号、Level、Rank等を理由に、その人物が作品評価・作品Rank・ランキングを支配する構造にはしない。SCOUTの公開実績は発掘文化・自己表現・発見導線の補助として扱い、人間読者全体の評価を置き換えない。

### 49.2 Scout XP と Scout Point の完全分離

SCOUT RECORDには、Scout XPとScout Pointの2系統を持たせる。

Scout XPは、読者としての成長、Scout Level、Scout Rankを表す。消費しない。

Scout Pointは、将来消費できる報酬資源とする。正式リリース後、AI利用特典・AI Credit等への交換機能を解放する予定とする。

XPとPointは同一通貨にしない。

XPを消費してAIを使う設計にはしない。

Scout Pointはβ版から獲得・残高表示する。ただしβ版では原則としてまだ使用できない。

β版では、将来利用できるPointが貯まっていくこと自体を参加・継続のモチベーションとして利用する。

AI Creditへの正式交換レート、金銭換算価値、交換単位は現時点では確定しない。AI原価・利用実績等を見て将来変更可能な設計とする。

基礎的な作品発見・読書体験をScout PointやAI Creditの保有有無で有料化しない。

### 49.3 Scout XPのβ正式条件

第38章の既存Scout XP仕様を維持する。

#### 有効読書

有効読書1作品につき2 XP。

1日の獲得上限は5作品、最大10 XP / 日。

同一作品から有効読書Scout XPを獲得できるのは原則として生涯1回。

有効読書の詳細判定は第38章を正本とし、本文到達、サーバー側時刻由来の前面滞在、スクロールその他の操作、短いエピソードへの補正、バックグラウンド放置除外、自作品除外、機械的反復除外等の既存条件を簡略化・削除しない。

#### LIGHT SEED

LIGHT SEED使用時のScout XPは第38章の既存値を維持する。

- GOLD：30 XP
- SILVER：20 XP
- BRONZE：10 XP
- 月間11個をすべて使用した場合、LIGHT SEED使用だけで最大260 XP

#### ☆評価

- 1作品につき3 XP
- 1日5作品まで
- 最大15 XP / 日
- 同一作品では生涯1回
- ☆の高低でXP量を変えない
- 評価変更・削除・再評価で重複付与しない

#### 有効コメント

- 有効コメント1作品につき5 XP
- 1日3作品まで
- 最大15 XP / 日
- 同一作品・同一日は最初の1回だけ
- 文字数でXPを増減しない
- 無意味投稿、コピー、BOT、機械的大量投稿等を対象外・取消可能とする

#### 発掘成功・NOVA予見

LIGHT SEED送信時点の作品Rankを基準Rankとして保存する。

原則180日以内の最高到達Rankを確認する。

基準Rankから+2 Rank、+3 Rank、+4 Rank、+5 Rankを段階的な発掘実績とする。

発掘成功の入口は+2 Rank。

+3、+4、+5へ成長した場合は、より上位の発掘実績として扱う。

既に獲得済みの段階を再度通過しても同一報酬を二重取得させない。降格後に同一Rankへ戻った場合も再取得不可とする。

第38章の既存発掘Scout XPを維持する。

- +2 Rank：基礎150 XP
- +3 Rank：基礎300 XP
- +4 Rank：基礎600 XP
- +5 Rank：基礎1,000 XP
- NOVA予見：基礎80 XP

LIGHT SEED種類による発掘Scout XP倍率も維持する。

- GOLD：×2.0
- SILVER：×1.5
- BRONZE：×1.0

上位段階へ進んだ場合は既存どおり累計Scout XPとの差額だけを追加する。

自作品、同一作品の重複、機械行動、不正行動に関する既存除外・取消原則を維持する。

### 49.4 Scout Pointのβ暫定配点

Scout Pointは単純なクリック回数や閲覧回数ではなく、「成長・発掘・実績」を中心に付与する。

通常の有効読書、☆評価、有効コメント、LIGHT SEEDを置いただけの行為には原則としてScout Pointを直接付与しない。それらはScout XP側で評価する。

#### Level Up

- Level Up：+5 Point

#### 発掘成功

- +2 Rank：累計20 Point
- +3 Rank：累計50 Point
- +4 Rank：累計100 Point
- +5 Rank：累計200 Point

上位段階へ進んだ際は差額のみ追加する。

例：

+2達成で20 Point
→ +3達成時に追加30 Point
→ 累計50 Point

#### NOVA予見

- NOVA予見：+25 Point

### 49.7 読者称号のScout Point

- Hard：5種類

### 49.11 β版Scout Level Cap

β版のScout Level上限はLv.30とする。

Lv.30到達後は、

- Scout XPはそれ以上蓄積しない
- Lv.30以降に発生したXPは消滅する
- 正式リリースへ持ち越さない

ことを明確にする。

正式リリース時は、β中にどれだけ活動していても最大Lv.30から開始する。

Lv.30到達後に発生したXPをLv.31以降用に保存しない。

正式リリース時には、Lv.30 / 次Level向けXP 0からLv.31以降の成長を開始する。

ただしLv.30到達後も、

- Scout Point
- 称号
- 発掘実績
- その他の対象実績

は引き続き獲得できる。

このためβでLv.30へ到達したユーザーにも活動を続けるメリットを残す。

### 49.12 Lv.30到達時の告知

Lv.30到達時には通常XPバーから「β LEVEL MAX」表示へ切り替える。

ユーザーには、少なくとも以下の趣旨を明確に表示する。

「β版のレベル上限はLv.30です。
Lv.30到達後に獲得条件を満たしたXPは蓄積されず消滅します。
Scout Point・称号・発掘実績は引き続き獲得できます。
正式リリース後、Lv.30以降のレベルが解放されます。」

この仕様はβ開始前・β利用中にも分かりやすく告知する。

XP消滅条件を隠さない。

### 49.16 Scout Point Ledger

Scout Pointは単一の残高数値だけで管理しない。

全増減をLedgerとして記録する。

例：

+20 発掘成功
+5 Level Up
+10 読者称号
-20 不正報酬取消

残高を管理者が直接書き換える設計を基本としない。

Point状態は少なくとも、

- confirmed / 確定
- pending または frozen / 保留・確認中
- cancelled / 取消

を扱えるようにする。

異常検知時は対象Pointを凍結可能とする。

調査後、正当であれば確定へ復帰し、不正であれば取消とする。

取消も元記録を物理削除するのではなく、逆仕訳・取消記録を残し、監査可能にする。

正式リリース後にAI Credit交換が始まった場合は、

- 総保有Point
- 利用可能Point
- 確認中Point

を分離できる構造にする。

Point残高はLedgerから再計算・監査可能であることを基本とし、表示用残高を唯一のSource of Truthにしない。

### 49.17 不正Scout Point対応

第13章・第14章の包括的不正原則と段階的対応を維持する。

Scout Pointについては、例えば以下を基本とする。

軽微・初回：
対象Point取消。

反復：
一定期間Scout Point獲得停止。

明確なBOT、複数アカウントによるファーミング、談合、組織的な不正：
関連Point取消 ＋ Scout機能制限。

重大・反復：
アカウントレベルの措置も可能。

複数アカウントを持つこと自体を即不正とせず、それを利用してPoint、称号、発掘、評価、露出等を不当に操作する行為を対象とする。

自動検知だけを根拠に重大措置を機械的に確定せず、必要に応じて凍結・記録・確認を行う。

### 49.18 β版SCOUT RECORD KPI

第22章の「LIGHT SEED / SCOUT RECORD」KPIを正式なβ計測項目とする。

SCOUT RECORDが成功しているかは、単なるLevel上昇数、称号獲得数、Point発行量ではなく、

「読者がより多くの作品を読み、新しい作品を発見し、NOVELIGHTへ継続して戻ってくるか」

で判断する。

特に、SCOUT RECORD利用者と非利用者の7日・30日継続率、1読者あたり閲覧作品数、新規作者作品・低Rank作品への流入、発掘後の作品成長、不正検知・Point凍結・取消を比較する。

### 49.19 SCOUT RECORD UIデザイン方向

SCOUT RECORDの見た目は、共有済み参考画像の方向性へ近づける。ただし完全コピーではなく、NOVELIGHTの正式UIとして再構成する。

- ゴールドを主要アクセント
- 高級感
- 羅針盤 / 星 / 発掘を想起させるモチーフ
- 大型ランクエンブレム

- 発光表現は過剰にしない
- ゲーム的だが読書サービスとしての可読性を維持

とする。

1. 現在Rank / Level / XP / 次Rank

### 49.21 守るべき不変原則

SCOUT RECORDの設計・調整では、以下を維持する。

- 評価される前の機会格差を減らす
- 課金で評価そのものを買わせない
- 読者が新しい作品を発掘する楽しさを作る
- LIGHT SEEDと発掘実績を中心にする
- ゲーミフィケーションは本来の読書・発掘・評価・創作を補強する
- Pointは目的ではなく補助報酬とする
- 不正・談合・複数アカウント悪用・BOTを前提に対策する
- βの実利用データから運用値を調整する
- 思想は固定し、手段・数値は改善可能とする
- 人気ユーザーが作品評価を支配する仕組みにしない
- 称号やPointのために無意味なコメント、高速巡回、無差別評価、SEED乱用が最適解にならないようにする
